TL;DR: Tejas chose one dedicated messaging agent on September 21; the Inbox router chose to run it on the Mac because the original text sending path used Messages there. That placement unnecessarily makes email drafting and sending wait for a sleeping laptop, even though the personal email connection and send now run on the always-on server. The broader failure is that routing, capability claims, and completion reports can be plausible without proving the specific action will work.

This is a read-only retrospective. “Confirmed” means the supplied record shows the decision, behavior, or result. “Inferred” marks a proposed system explanation. Source timestamps below are UTC.

## 3. Why the messaging agent is on the Mac, and what sleep does

**Who decided:** Tejas chose a single dedicated messaging session and, in his September 21 wording, included future messaging feature work. The Inbox router made the *placement* choice: it told him the session would start on the Mac “where Messages lives,” then addressed the first request to that Mac session at 05:33 UTC. I found no quoted Tejas decision that the entire agent, including email, had to live there. [Tejas’s choice and router response, September 21, 04:48](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/inbox-router-concierge3172-before-0926.txt:21120>); [first Mac session, 05:33](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/messaging-agent-mac15.txt:2>).

**What needs the Mac:** Reading the local Messages conversations and sending or confirming iMessage, SMS, or RCS through the Mac’s Messages path. The server can retain the request, compose words, store a draft, use its personal Google connection, and send an authorized email. The Sophie check-in ultimately left through that server connection at 22:19 UTC, with a Gmail sent receipt. [Original Messages flow](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/messaging-agent-mac15.txt:19>); [Sophie receipt](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/messaging-agent-mac15.txt:6178>).

**When the Mac sleeps today:** A request to its session is retained as waiting for the Mac and retried when it answers. The requesting agent gets an overdue note after 30 minutes; ordinary sleep itself does not notify Tejas. The archived transcript can be read, but the same Mac session does not automatically run on the server. Consequently an agent-routed email request waits for the Mac messaging session even though the email effect could run on the server. A text send also waits for the Mac’s actual Messages capability. [Peer behavior contract](</root/workspace/slack-concierge/docs/runbooks/PEER-INSTANCES.md:360>).

## 4. Why the discovery test passed

The morning test asked four fresh agents on both machines to locate: project setup, Spotify status, and who would keep a **text draft**. It was read-only. None was asked to send personal email, distinguish the app’s Google connection from the unsigned personal Google command, or handle a sleeping Mac. Its “all three” result was true for those prompts and too broad as reassurance about the whole map. [Exact test prompt](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/capability-map-refactor-concierge3865.txt:1118>); [reported result](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/inbox-router-concierge3172-since-0926.txt:7142>).

A check that catches this incident would give a fresh agent the exact Sophie-style instruction, ask it to identify the owner, machine, account, and current readiness, then compare those answers with the **server connection’s actual status and permitted operation**. It would fail if the agent selects an unsigned second path, asks for credentials already held by the owner, routes email execution to a sleeping Mac without explaining the wait, or calls a draft “sent.” The later Byron dry run covered some of the routing questions *after the map repair*, but it explicitly performed no send and cannot prove live delivery or laptop independence. [Later dry-run prompt](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/capability-map-refactor-concierge3865.txt:2434>); [later result](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/inbox-router-concierge3172-since-0926.txt:10735>).

## 5. Scrap, change foundations, or keep as is?

| Option | Where it wins | Where it loses |
| --- | --- | --- |
| **Scrap and rebuild** | A clean opportunity to define machine and role boundaries together. | It would have to migrate retained conversations, drafts, account consent, request identity, and uncertain sends without duplication or loss. No evidence here measures that cost or shows the existing ownership ledger must be discarded. A rewrite may reproduce the same mistaken assumptions. |
| **Keep the records and change the specific foundations above** | Preserves the working server send, retained history, and existing Mac Messages path while removing the laptop dependency from email and making capability and completion claims checkable. | Requires an approved architecture and careful migration of the long-running agent’s open work. Effort and outage risk are **unmeasured**. |
| **Keep as is** | Avoids immediate migration and preserves current behavior. | Leaves the documented Mac dependency for email, fallible capability discovery, and repeated reliance on an agent’s judgment to distinguish progress from fulfillment. The September 29 incidents show those costs are already real. |

My recommendation against a wholesale restart is **conditional**, not a claim that the current foundations are sound: retain the records and working owner services, then bring Tejas one concrete architecture proposal for the session, machine, capability, and outcome changes. That proposal needs his approval under the standing foundation rule. ## 6. Additional finding

The capability map’s **current** “personal Gmail cannot be read or searched by agents” row is too absolute for the supplied history: a Codex session did search personal Gmail and verify a draft through a Gmail connector on September 28. The same connector was unavailable in that session on September 29. That does **not** prove it is dependable now; it shows that access differs by agent session and time. A truthful capability description needs to distinguish “this owner offers a reliable operation” from “a particular session happened to have a connector.” [Current map row](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/capability-map-SKILL-current.md:42>); [successful September 28 search and draft verification](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/email-sophie-server-concierge3844.txt:187>); [unavailable September 29 session](</root/workspace/slack-concierge/tmp/reviews/retro-2026-09-29/sources/email-sophie-server-concierge3844.txt:457>).

### Ranked proposed changes

1. **Approve an always-on owner for email and drafting, with the Mac limited to Messages-dependent operations.** This removes the clearest unnecessary availability failure.
2. **Make each capability’s owner expose current readiness and an operation-specific result.** The map should point to that truth and refuse an unsigned substitute path.
3. **Make the Inbox preserve the requested effect until it has the corresponding receipt.** Show progress, blocked prerequisites, questions, and completion distinctly; retain Tejas’s words beside any broadened interpretation.
4. **Audit claims at their actual boundary before reporting them:** account authentication, provider delivery, deployed behavior, and Tejas’s live product use. Label dry runs and simulations.
5. **Keep the shipped blocked-work account notice rule narrow** and verify it from actual waiting work, without reviving ordinary account banners.

**Could not verify:** the Mac’s live state at the moment of this report; the exact current behavior of every email path after the evening changes; whether the later dry-run documentation has reached every running session; and the full implementation status of the September 25 latency proposal. No commands that change state or agent-run tests were used.
