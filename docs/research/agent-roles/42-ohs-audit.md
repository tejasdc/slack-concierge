# OHS / DKR / CoDIAK audit — how closely Thinkering followed Engelbart, and how well that held up

Read-only investigation. 2026-09-26.

## 1. Where the intent was recorded

**It is explicit in the founding spec, not folklore.** `/root/workspace/thinkering/DESIGN-SPEC-v0.6.md` §3 is literally titled "Engelbart A/B/C bootstrapping" and §4 "CoDIAK operating loop" (lines 167–239), with a CoDIAK diagram (External reality → Human+AI dialogue → Claims/Decisions → Action → Artifact → Verification → Learning → Pattern → Skill, looping). §5 "One substrate, many projections" (lines 245+) is the DKR claim in different words: no disconnected journal/chat/task-list/project-notes/decision-record/flashcard/pattern-database/agent-transcript/skill-document stores — one Object store, many views. The literal strings "OHS" and "DKR" do **not** appear in either DESIGN-SPEC-v0.5.md or v0.6.md — those acronyms live in the *research trail behind* the spec, not the spec text itself.

**Primary research citations** (`docs/research/sources.md`): `ENGELBART` (Augmenting Human Intellect, 1962), `ENGELBART-CODIAK` (Engelbart Institute glossary — "CoDIAK and collective development/integration/application of knowledge"), `ENGELBART-BOOTSTRAP` (Call to Action — A/B/C work), plus `KAY` (Alan Kay, Early History of Smalltalk). `docs/design-review.md` (2026-09-06, "Prepared as historical input to v0.6, before the application build") is the fullest discussion: its "Engelbart lens" section states directly that Thinkering "aligns with [augmentation-as-a-whole-system] through learnable interaction, deliberate cognitive distinctions, A/B/C improvement and practice," and criticizes it for being "more specific about individual reflection than collective knowledge development" — i.e. CoDIAK's collective half was deferred by design (§82), not forgotten.

**Tejas's own words, dated, from `tmp/brainstorm-threads/prior-thinking.md`** (compiled 2026-09-20 from ChatGPT session snapshots, session `WzIsMzIwOSwxXQ` / concierge:3209, ~2026-08 to 2026-09-19):
- On why project management shouldn't be a separate app: *"when I'm journaling, I'm not just talking about my life. I'm also just sometimes talking about my project and how those projects made me feel... it's all kind of interconnected."* Named reference: **"Engelbart's OHS (Open Hyperdocument System)."**
- On attractors as a DKR mechanism: *"attractors are almost a mechanism inside that integration process: places where weak improvement signals can accumulate until they become strong enough to change how work is done."*
- The Engelbart tricycle/bicycle line, invoked independently in at least two separate sessions (design spec discussion and the "oral technology" topic-thread discussion) as a deliberate argument for keeping some friction rather than chasing ease-of-use.
- `vault/projects/agent-ecology/notes/TODOS.md` has a standing TODO: *"should include the attractor pattern for learning from mistakes, and generally a codiak loop implemented with a DKR and OHS substrate"* — the three acronyms as one named joint requirement, still open.

**Deepest secondary source**: `/root/workspace/vault/tmp/reviews/research-craft-codiak.md`, a research digest (scope: Ahrens/Newport/Engelbart for a *different* project, the journalmaxx Obsidian vault, not Thinkering) that quotes Christina Engelbart's OHS Framework and Eugene Eric Kim's *Towards a Standard Graph-Based Data Model for the OHS* directly, with an explicit 12-row OHS requirements checklist. That checklist is the template this audit's §2 below adapts to Thinkering. `/root/workspace/vault/tmp/reviews/spec-v0.5-review.md` (2026-09-06) is a second, independent 20-criteria review of the v0.5 spec that separately flags relations-should-be-objects, agents-as-sync-participants, and the "evolve mode" gap.

**Verdict recorded at the time**: `docs/design-review.md` line 7: *"Approve the research direction. Do not freeze the universal schema yet. Build a narrow, instrumented substrate rather than a universal application framework."* — i.e. the OHS/DKR/CoDIAK ambition was accepted as the target, but the reviewer (and the spec itself, §2.4: "do not build a universal ontology from an armchair") deliberately sequenced a narrow substrate first. `docs/object-model-audit.md` and `docs/requirements.md` are the two documents that tracked what shipped against that ambition; `docs/design.readme.md` is current, living architecture.

## 2. OHS requirement-by-requirement scorecard

Evidence is code paths and doc lines, checked directly in `/root/workspace/thinkering` (packages/core/src, packages/application/src, apps/web/src) as of 2026-09-26.

| OHS requirement | Rating | Evidence |
|---|---|---|
| **Mixed-object documents** (one interface over notes, code, transcripts, images, audio) | **Partial** | `ObjectDetail` (`packages/core/src/workspace-types.ts:28-55`) is one typed union covering block/source/relation/loop/work-intent/session/experiment/workflow/agent-session/change-set/verification/skill — genuinely one substrate for prose, decisions, agent runs and code changes. `source.format` covers `'note'|'transcript'|'reading'` only; images/audio are handled as attachment rows in Concierge's capture pipeline (`bot/src/` — "Retained audio attachments keep their original bytes and an optional transcript in the same attachment row"), a *separate* store from the Thinkering Object graph, joined only at import time. Git commits appear as `change-set`/`verification` objects referencing `baseCommit`/`headCommit`/`fingerprint`, not as first-class diff content. |
| **Explicit structure** (addressable hierarchy, not free text) | **Met** | Every object has `parentId`, `position`, `projectId` (`workspace-types.ts:57-61`); `outlineParent()` and `assertForest()` (`workspace.ts:65-79`) enforce a cycle-free forest and reject structural corruption at commit time, not at render time. |
| **View control** (multiple views over the same content) | **Met** | `Lens` (`kind:'lens'; query:LensQuery`) is a versioned, saved query object (`workspace-types.ts:18,42`); Timeline/Board/Review/Reading/Practice/Work are named projections over the same Objects (`docs/design.readme.md` line 11-12: "Timeline, thread outlines, Board, Review, Work, Reading and Practice project the same semantic substrate"). Kim's OHS "headers only / first line of every paragraph" granularity is not implemented — lenses filter/sort objects, they don't sub-view inside one object's text. |
| **The Journal — immutable record with citable addresses** | **Met** | `docs/design.readme.md` line 69: *"One immutable journal stores semantic operations, incremental editor updates and atomic checkpoints... Old evidence never follows a mutable head."* Implemented literally: `materializeWorkspace()` (`workspace.ts:17-46`) replays an append-only, causally-clock-ordered `WorkspaceOperation[]` log; `ID_REUSE`, `MISSING_PARENT`, `INVALID_CAUSAL_CLOCK`, `DUPLICATE_OBJECT_ID`, `IMMUTABLE_SOURCE`, `IMMUTABLE_REVIEW` are thrown, not silently allowed. An `ObjectRef = {objectId, revision}` is a citable address to one exact revision, pinned by relationships and evidence (see below). |
| **Granular addressability of every object** | **Met** (down to the object; not sub-object) | Every Block, Relation, Loop, Decision, AgentSession, ChangeSet etc. is independently `objectId`+`revision` addressable, matching Kim's "link to objects more granular than a document" at the block level. It does **not** reach paragraph/pixel/frame granularity inside a single rich-text block — `richTextPlainText` mismatch is checked (`workspace.ts:83`) but there's no sub-block anchor type; the design review itself flagged this (finding 2: "a naked character offset is not a durable citation" [PROSEMIRROR-GUIDE]) and it's still an open text-anchor problem per `docs/design.readme.md`'s "Text and durability" section. |
| **Hyperlinks to any object** | **Met** | `RelationshipForm` (`apps/web/src/relationships.tsx:41-78`) links any two objects with a typed `RelationKind` from an 18-member vocabulary (`supports, contradicts, evidence-for, caused, blocks, depends-on, implements, tests, resolved-by, supersedes,` etc. — `workspace-types.ts:10`), each with a UI-surfaced epistemic caveat (e.g. `caused: 'The source is claimed to have caused the target. Record the basis for this causal claim.'`). Relation is itself a first-class `Revision` object (`workspace-types.ts:31`), with its own accept/retract lifecycle and history — this is the exact fix the spec review demanded (finding 2, and independently vault's spec-v0.5-review.md #3: "Relations are not Objects... expensive to retrofit... costs nothing now"). It got retrofitted before ship. |
| **Back-links** | **Met, but unnamed** | No literal string "backlink" exists anywhere in the codebase (checked). The feature exists under a different name: `RelatedEvidence()` (`apps/web/src/relationships.tsx:100-117`) filters all relation-objects where `detail.from.objectId===object.objectId \|\| detail.to.objectId===object.objectId`, buckets them `incoming`/`outgoing`, and separately surfaces `contradicts` as "counter-evidence." This is a fuller back-link than OHS asked for (it carries the relation's reason text and epistemic status, not just a pointer). |
| **Shared catalogs / directories** (multi-user library) | **Missing — by explicit deferral, not oversight** | `docs/design-review.md` line 19: *"collaboration is explicitly deferred (§82)."* `requirements.md` line 79: *"Native apps, public multi-user collaboration... are not substitutes for requested personal workflows."* This is a single-operator system; there is no shared namespace across users. Within the one user's graph, `Command`/`Workflow`/`Lens`/`Binding`/`Skill` are a de-facto personal catalog (versioned, reusable definitions distinct from their runs — `workflow` vs `workflow-run`, `skill` vs `skill-transfer`). |
| **Library / reference system** | **Partial** | `Source` objects (`kind:'source'; format; origin; importedAt; checksum`) are the reference/citation layer: `requirements.md` line 76: *"Existing Obsidian notes remain authoritative in their vault. Import is an explicit read-only copy with provenance, not migration."* `IMMUTABLE_SOURCE` (`workspace.ts:88`) throws if a Source's text or detail changes after import — enforced immutability of the reference copy, matching OHS's separation of the living document from its cited sources. It covers notes/transcripts/reading only, not a general external-document registry (no email, no arbitrary file types). |
| **Integrated document and dialog** ("instant access to the corresponding dialog, commentary, and design rationale" — DKR litmus test) | **Met, strongly** | `AgentSession` objects carry `disclosed: ObjectRef[]` (what context was shown to the model) and link back to the `intent` they served; `Relationship.reason` is mandatory free text justifying *why* a link exists, not just that it exists; `Loop.rationale` is required for reopening (`HUMAN_REOPEN_REQUIRED`, `workspace.ts:98`). Decisions/loops cite `basis: ObjectRef[]` and reject empty basis for `fact`/`decision` closures (`MISSING_BASIS`, `workspace.ts:96`). This is close to Christina Engelbart's DKR litmus test ("hit a brick wall due to an earlier design flaw, instantly get the design documents... with instant access to the corresponding dialog, commentary, and design rationale") for the personal, single-user case. |
| **Access control** | **Diverged, deliberately** | `docs/design.readme.md` "Trust" section: passkeys + owner recovery gate the app; "Server agents can read disclosed synchronized notes; this is not end-to-end encryption against the machine administrator." No per-object or per-user ACL exists (single operator), but capability-scoped agent disclosure is real: `canAuthorDetail()` (`workspace.ts:80-83`) restricts which `ObjectDetail.kind` each actor kind (`human`/`agent`/`system`) may author — an agent literally cannot write a `loop` closure of `fact`/`decision` or endorse a proposal; only a human can (`HUMAN_ENDORSEMENT_REQUIRED`, `workspace.ts:85`). OHS envisioned access control as *permissioning within a shared multi-user repository*; here it's collapsed to a single trust boundary (device/passkey) plus an internal human-vs-agent authority split — same goal (protect the DKR's integrity), different mechanism because there's one user. |
| **Personal signature / provenance** | **Met** | Every `Revision` carries `actor: {id, kind:'human'|'agent'|'system'}` and `at` timestamp (`workspace-types.ts:8,62`) — non-optional, checked at commit. At the delivery layer (slack-concierge), `doorOf()` in `session-message-author.ts` stamps every message with which door it came through ("You · iPhone Action Button" vs. an agent's own name), and `agentTestSource`/`X-Concierge-Agent-Source` let an agent test its own delivery path without impersonating the human — "Provenance, not prisons" is the house rule. |
| **External document control** (cite without absorbing; original stays authoritative elsewhere) | **Met** | `requirements.md` line 76-77 and `IMMUTABLE_SOURCE`: an imported Obsidian note or transcript is copied in as a checksummed, immutable `Source`; the vault file remains the authority for editing, Thinkering's copy is read-only evidence. Same pattern for git: `ChangeSet.baseCommit/headCommit/fingerprint` reference commits without duplicating the diff. |
| **Interoperability** (open format, no lock-in) | **Met** | `requirements.md` line 58: *"Export includes complete history and references; restore validates the complete archive before merging history."* Markdown is the canonical text encoding (CommonMark/GFM, line 90); `docs/design.readme.md` states RxDB/SQLite are implementation choices behind ports, explicitly swappable ("A library swap must preserve behavioral contracts... not merely rename an interface"). |

**Threads/topics, notes, captures — status not in the table above:** the *topic/branch/glyph* model that Tejas converged on independently in the "Oral Technology" ChatGPT session (Topic = territory, Branch = a directional line of inquiry, Thought = atomic unit typed by a glyph, View = computed not tagged) is recorded as an accepted design in `prior-thinking.md` §3 but — per that same digest's closing note — **does not appear implemented in the Thinkering codebase**; Thinkering shipped Timeline/outline-thread navigation instead (`docs/design.readme.md` "Timeline projects existing root notes and Sources in creation order... with children and siblings inline"), which satisfies the addressability and hierarchy requirements above but not the specific Topic/Branch/glyph vocabulary he designed for it.

## 3. A/B/C activity levels — where each happens today, and where it's stored

The spec is explicit that A/B/C are "not separate applications... properties and projections over shared Objects" (`DESIGN-SPEC-v0.6.md:208-210`). Mapped onto the actual running system:

- **A-level (doing the work)** happens inside Thinkering itself as ordinary object mutation — capturing notes, closing loops, running workflows, agent sessions doing chat/extract/develop work (`agent-procedure.role:'procedure'`) — and, one layer out, as ordinary project work in `~/workspace/<project>` repositories. Storage: the Object/Revision graph (`WorkspaceState.objects`) for in-app A-work; each project's own git history for code-shaped A-work. `WorkIntent.level:'A'|'B'|'C'` (`workspace-types.ts:36`) is a literal field on the object, so A/B/C is tagged data, not an inferred category — a WorkIntent can *declare itself* B- or C-level work at creation.
- **B-level (improving how A-level work gets done)** is split across two homes that don't yet share one substrate: inside Thinkering, `agent-procedure.role:'session-steward'` objects and `Pattern`/`Recurrence`/`Skill` facets are the designed B-track (a steward consolidates after sessions, distinct from the working agent — "prevents the same agent that made a decision from also becoming the unquestioned historian of why it was correct," `prior-thinking.md` §1). Outside Thinkering, B-level work is what actually accumulates today: per-project `AGENTS.md`/`CLAUDE.md` rules, catalog skills in `~/workspace/skills/*`, and the "lessons" mechanism (`docs/LESSONS.md`) — e.g. this repo's own CLAUDE.md is almost entirely dated B-level corrections ("a session amended a pushed commit... Tejas: 'Why are we...'" → a new refused-history-rewrite rule). Storage: git-tracked instruction files and the skills catalog repo, not the Object graph.
- **C-level (improving how B-level improvements are discovered and transferred)** is the least implemented in-app: `agent-procedure.role:'skill-steward'` and `skill-transfer` objects (`workspace-types.ts:41,55`) are the designed mechanism — a skill only becomes `confidence:'validated'` after a recorded `skill-transfer` with an independent observation, not by assertion. In practice today, C-level work is this kind of design/audit session itself (a fresh Opus session auditing the system against Engelbart's own program, reasoning about the mechanism by which B-level rules get written) plus the global CLAUDE.md's own meta-rules ("Skills improve through progressive overload," "the golden rule: rely on systems, not good intentions," the whole Model-selection escalation ladder). Storage: this file you're reading (`tmp/reviews/`, ephemeral) feeding into `docs/plans/`, `AGENTS.md`, or `~/workspace/skills/docs/LESSONS.md` (durable) — i.e. C-level output is *supposed* to migrate from a throwaway review into a durable instruction artifact, mirroring the spec's own three-timescale design (participant → session steward → practice steward) even though that three-tier stewardship is not yet running inside Thinkering's own agent-procedure objects for real workloads.

**Net assessment:** the *object model* for A/B/C/CoDIAK/DKR is substantially built and enforced by runtime invariants (immutable journal, typed relations-as-objects, human-only endorsement, granular per-object provenance) — closer to the OHS ideal than the 2026-09-06 design review anticipated at that stage. The *collective* half of CoDIAK (multi-user Collective IQ) was deferred on purpose and remains absent. The *lived* B/C loop — where a hard-won lesson actually becomes durable — currently runs mostly outside Thinkering, in git-tracked instruction files and the skills catalog, not inside the Object graph the spec designed for exactly this purpose; that is the one place the system as operated has diverged furthest from the CoDIAK diagram's closed loop back into the same substrate.
