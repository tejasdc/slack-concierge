# Mac agent awareness

The Mac owner now refuses new or addressed peer work without a named Mac-only need. The
request must state the relevant native iOS, Mac app, Mac file, Mac screen, Messages, or
explicit human Mac need. A pre-tool hook also refuses common browser and foreground-control
commands in Claude and Codex turns, including server SSH commands aimed at the Mac. It allows
background Simulator command-line automation only with a native iOS need on that accepted
turn. Codex Computer Use also requires a recorded desktop-capable need, and Claude in
Chrome remains refused because it controls his personal browser. Concierge's own
provider sign-in repair request is the only Computer Use exception for the saved
Chrome account; the Mac owner checks the retained repair request before admitting it.
For Tejas's directly authorized, already-open thnkr.ing Safari web app and old-page
work, a Mac-app request must name its exact bundle and page IDs. Its retained provenance must
lead to a human input and a work effect; an informational request cannot grant
Computer Use. The Mac owner returns that provenance and reason to the hook,
rather than checking a list of past human input IDs. Computer Use admits a
direct `getApp` call selecting that bundle. Later passive reads must select the
bundle again and read it in the same Computer Use
program with a dedicated `var thnkrCanvasInspectionApp` handle, so a remembered
REPL handle cannot point the read at another app. The retained originating-human
input must be verified by the owner and the old-page need must name the same
bundle and page. This allows inspection of the existing Mac page for the
lekondo Canvas incident and later unsaved-writing recovery; it does not
authorize interaction, page reload, or draft disposal. Only the original
November 3 human authorization,
in a Mac-app request that also names Web Inspector, may make one exact-bundle `getApp` and
Option-Command-I call in the same Computer Use program to attempt to open the
Inspector on that app. The program uses a dedicated `var thnkrInspectorApp` handle:
the Computer Use REPL can retain earlier `let app` bindings, while `var` can be
reused for a later attempt. The action binds a fresh handle instead of trusting an
earlier REPL variable. This grants the first Inspector-opening probe, not Console
input, clicking, heap capture, or export: those need a verified target-bound route.
A generic Safari selector, another web app or browser, whole-screen call,
nested tool call, or an old-page Mac-app request without both IDs remains refused. The exception lives
only while the accepted Mac request is active. Selecting the app does not establish
that the requested page is still present; the Mac agent must inspect and report that
separately before acting on its contents. The shortcut's effect on this installed
Dock web app is not yet verified and must be observed after the Mac unlocks; do not
claim a page-memory recovery path based on this grant alone. The original
authorization, Canvas capture and recovery capture are recorded in the policy
check. A new human work request for that old page follows the same owner provenance rule
without adding its ID to source. Tejas's later instruction to stop recovery and retire
the 53-edit notice is a different scope: the page ID from recovery no longer describes
the current window. Its exact originating capture, recorded `mac-app` work need, exact
web-app bundle, and `exact53 retirement` purpose permit direct app selection and a fresh
same-program passive accessibility or screenshot read. A dedicated retirement handle
prevents a remembered Computer Use REPL variable from pointing at another app. The
old-page grants remain available for their earlier work. File-menu interaction and a
second window are not admitted by this read grant: the Mac agent must first read the
returned Computer Use API and actual app accessibility tree, then prove a target-bound
action and same-app window path before the guard can admit those separately. A shortcut
or assumed menu coordinate is insufficient. This keeps the current window and its data
untouched while the app-owned retirement consumer is prepared.
When Tejas answers a physical prerequisite in the same Inbox task, the Inbox's
forwarded reply has no provider run. Its retained forward request proves the exact
human reply, including when another agent request follows it. A later Mac request
from that reply may carry the earlier web-app authorization only when the owner
can verify the task link and the new Mac-app need names the exact bundle and page.
The same rule follows owner-recorded release-watch and work-request return inputs back to
that forwarded reply, checking each input's recorded source run and the watch, peer, or local
request that delivered it. A new agent request, an unrecorded service input, a changed
source run, or a return from informational work does not carry the grant.
For the November 3 instruction, the original human input belongs to the same worker
session and joined the turn started by that Inbox topic's linked dispatch. For the
Canvas capture, the reply must address that exact capture in the same Inbox topic,
and the work dispatch from that capture to the requesting Canvas worker must have
settled as needing the physical prerequisite. The peer delivery keeps the new
request as its immediate source and the original instruction or capture as its
scoped authorization. Neither provider-facing
text nor an agent-supplied old run can create this link. The Mac hook still checks
each Computer Use operation against the exact-app read-only policy.

The question gate accepts a device-only claim when its question names one action on a
physical device. The agent first uses its available device route. If that route reaches
a physical prerequisite such as unlocking his Mac, the question names that prerequisite.
Starting one named app on an e-reader, watch or TV can also be a physical prerequisite:
for example, KOReader must be started on a Kindle before it exposes an agent connection.
The required explanation says which route was tried and why the agent cannot do that
step itself. A generic request to open an app or website remains refused.
The ask is the question's first sentence, phrased "Can you unlock your iPhone?" or
"Please unlock your iPhone."; sentences after it may only state what the agent saw or
will do ("The device check reported it locked. I will handle the app inspection."). A
later sentence that asks him for more (addresses him, says "then", or is a question)
refuses the whole question, so app work never moves to him behind an unlock.

The Mac session owner observes Claude and Codex tool starts in the existing provider
progress stream. The server owner also observes tool calls that SSH to Tejas's Mac,
including a plain command and AppleScript from a server agent. For actions that can
visibly affect Tejas's Mac, it retains one
`mac_surface_activity` event per action kind and turn with the agent's exact session,
input, turn and a short action description. It does not treat this as a permission
request or block the tool. The event ID makes provider replay idempotent.

The first action of each kind in a turn is reported: installs through common package
managers, launchd loads, Chrome debugging, screen capture, AppleScript and computer
use, opening an application, and SSH to the Mac. This is evidence from the agent's tool request,
not a claim that macOS granted a permission or that an installation completed.
The SSH observation recognizes the Mac peer's registered SSH address. Tool activity
outside the observed provider stream is not covered. macOS remains
the source of truth for its own permission and login-item records.

Codex reports shell commands under the shell executable's name, including
`/usr/bin/zsh`; the SSH observer accepts that tool identity. The first marked
server SSH check on October 16 ran successfully but created no activity event
because this identity was missing. A later check must observe both the retained
event and phone delivery.

On October 16, a server Codex agent investigating thnkr.ing Capture ran a
read-only AppleScript login-item query through SSH. macOS showed Tejas an
`sshd-keygen-wrapper` request to control System Events, while the existing
Mac-only observer sent no notice. The agent told him to choose Don't Allow;
the query did not need that permission. This server-side observation closes
that measured attribution gap. A harmless SSH AppleScript call and the
resulting phone notice are the live acceptance check.

Thinkering's existing attention notifier subscribes to this event from both
Concierge peers. It resolves the current session to name the agent and task, then
sends one phone alert linking to that session. The session's Stop control cancels
running work; a completed action still has its retained record. The notifier
uses its existing target and delivery store. Replay is deduplicated by event ID,
and events older than ten minutes are not pushed after an outage.

The activity record still answers who did what and gives him the existing Stop path. The
new refusal is limited to browser and foreground control and does not revoke background
Mac-only automation.
