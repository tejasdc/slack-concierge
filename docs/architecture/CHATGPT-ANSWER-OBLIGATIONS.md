# ChatGPT answer obligations

This document describes the source contract. An admitted ChatGPT question remains owed until its answer reaches the asking session and the agent records how it handled it, or that same asker explicitly withdraws the question. An attempt result or a turn outcome is not the task's answer.

State card: the exact question is the entity; the server or Mac Concierge session coordinator is its sole writer. Its original request ID survives retries and releases. A retained cancel input or a received answer event is the evidence for closure. Provider failure leaves the duty open for receipt repair. A duplicate action repeats the same disposition, and an unstarted queued repair is withdrawn when the duty closes. The operating profile is one person, two machines, and a small number of concurrent questions.

The requesting agent can cancel its own ChatGPT request, including one routed through a peer. A completed, retained cancel action from that exact session closes only the corresponding question as `resolved` with `withdrawn_by_asker` evidence; a failed attempt or timeout does not. The coordinator applies this in the cancel transaction, checks it again before admitting repair, and reconciles older completed cancels at startup. This prevents a canceled question from waking its asker after a release.

An asking agent can also handle a failed question as `superseded` when a later ChatGPT answer substantively covers it. It cites the later request, its exact received answer event, and a concrete coverage reason through `sessions answer`. The owner requires the original attempt to have settled failed, checks that the later request was created afterward, belongs to the same asking session and task when that task is recorded, reached ChatGPT, and returned its answer to that session. This records the agent's coverage judgment without pretending the original failed send succeeded. The original receipt and failure remain in history. Closure withdraws any repair input that has not started; an already running repair turn sees the closure when it next acts.

## Ownership and identity

The owner records the question, its request ID, the asking session, the ChatGPT target, and one exact task reference in the same transaction as request admission. Task references are a local request, a peer-delivered request qualified by the origin instance, an external request, or an accepted direct human turn input. A later human steering input must explicitly select an existing task. Source time, session membership, and the originating human alone do not establish task identity. An idempotent ask repeats the same identity; changed words, target, or task conflict.

An accepted provider handoff transfers each open answer duty to the successor in the same transaction as its sent requests. The original question, request and answer-event IDs stay fixed, as does original input provenance. The successor records handling with its own accepted source input after the exact return is acknowledged. At startup, the owner reconciles open duties left with predecessors by older accepted handoffs; it withdraws unstarted repair inputs there and schedules the current successor for repair without sending another question to ChatGPT.
An unacknowledged answer return holds a new handoff until its exact receipt arrives. Recovery of an older accepted handoff consults that retained receipt before moving the duty; a missing receipt stays open and is logged for repair.

The task's final reply checks the unresolved obligation index. A completed reply is refused while any exact answer remains open. A failed or needs-decision reply may report the blockage only when it cites every open question with `--open-chatgpt`; each cited obligation remains open for repair. A direct human input with an open obligation cannot declare a terminal done, response, or failed outcome. A later source input that explicitly selected the direct task is linked to it and has the same terminal guard. An automatic result marker is recorded quietly as `finished_without_saying` while the direct obligation remains open; explicit `sessions outcome` still refuses terminal closure. Independent tasks use different keys and can finish separately.

## Answer and repair

The original provider attempt and request ID remain the recovery target. A failed or ambiguous attempt enters receipt reconciliation. The owner never treats a timeout, canceled turn, or stalled reminder as proof that the browser did not send the question, and it does not create a replacement browser send from them. An answered request enters return-pending; only an acknowledged return input advances it to handling-pending. Grouped returns retain a separate answer event for every question even when they share one accepted input.

A provider's definitive `NOT_SENT` or `SEND_FAILED` evidence can requeue the same native turn with capped backoff. `NOT_SENT` is a transient pre-Send wait and does not spend the finite provider retry budget. `SEND_FAILED` can mean a persistent sign-in or account failure, so it spends that budget. Once repeated failures exhaust it, the original task remains open, the asking agent receives the failed attempt state, and receipt repair becomes due. An ambiguous dispatched operation remains reconciliation-only until its original receipt is known.

Thinkering includes the retained pre-Send stage and original browser failure code in failed start and reconciliation receipts and terminal observations when its receipt proves Send was not pressed. Concierge preserves the generic `SEND_FAILED` retry classification while reporting that specific cause to the asking agent and routing sign-in, account-mismatch and human-check failures to Tejas. Older Thinkering releases omit these optional details; those failures still exhaust the finite retry budget and remain visible for receipt repair. The native result event predates this added result field, so Concierge compares it with the retained observation after excluding only the added pre-Send detail.

An attachment that ChatGPT explicitly rejects before Send cannot succeed on that immutable native run. The asking agent uses `sessions ask <original ChatGPT address> --for-task <same exact task> --correction-of <original request ID> --file <corrected file> -- <original question>`. The owner reconciles the original run with Thinkering and requires its terminal `CHATGPT_ATTACHMENT_REJECTED` receipt, no acknowledgement, no provider turn or answer text, and unchanged conversation binding. The attached file must have changed bytes. Admission then records a new request attempt under the **same answer obligation** and task; the failed original request and receipt stay in history. A failed, ambiguous, acknowledged, or already answered original request cannot use this path. The corrected attempt's answer returns to the original asking session and still needs explicit handling.

A Mac-origin ask reaches ChatGPT through a peer request. Its correction keeps the new request identity and file bytes on the Mac while the server is offline, with the original obligation still active. The Mac delivers the correction through a dedicated versioned peer route. The server checks its own original delivery, task, target, question, changed file bytes and fresh browser receipt before admitting the corrected input; an older receiver refuses the route. The server's accepted receipt carries the original run proof back to the Mac, which then activates the corrected attempt under the original obligation. A lost response retries that same correction request ID. No offline queue state or copied peer status is treated as proof that Send never happened.

For an older failed request whose original native run is terminal, the asking agent uses `sessions chatgpt-recover <original-request-id> --action-id <stable-action>` from its current admitted run. The owner reads Thinkering's retained receipt and requeues only that original run if the receipt proves no send, no acknowledgement, no result text, and unchanged binding. The command retains its own action receipt and does not create another question. The due scanner observes the original requeued run before admitting repair. A dispatched or ambiguous run is refused and remains in receipt reconciliation. In the same native run, definitively unsent `NOT_SENT` attempts use capped provider backoff without finite retry exhaustion; `SEND_FAILED` spends the finite retry budget and surfaces a persistent refusal while the answer duty remains open.

If the request was already marked failed, the coordinator can restore its answer only when the original dedicated native turn has finished and retained ChatGPT evidence proves the same run, input, conversation, acknowledged send, provider turn, and exact answer text. Proof is a completed start or reconciliation receipt, or a retained start/reconciliation receipt paired with its completed result event. It supersedes the owner-generated failed final while retaining that event and its earlier return as history. A new final for the **same request and obligation** carries the answer to the original asking session; there is no replacement question or browser send. If the original request asked for work, its work disposition remains undetermined, while the confirmed answer satisfies the separate question obligation and still requires handling by the asker.

The asking agent uses `sessions answer` with the exact obligation and answer event to declare that it used the answer, supplied missing context in an attached follow-up, or narrowed its conclusion with a concrete reason. This is a process attestation; the owner does not infer substantive answer quality from prose. A missing-context follow-up is a new, explicitly attached question in the same ChatGPT conversation after the prior answer reached the asker. It is not a retry of an ambiguous send.

Failed attempts, missing return receipts, unhandled answers, and old-peer holds carry an indexed due action. The existing session coordinator admits a service repair input with the original obligation and request identities, advances its due time before dispatch, and wakes again if that repair turn settles without resolving the duty. A returned but unhandled answer produces a handling prompt, without asking the agent to inspect or resend the browser operation. After three settled repair turns with no new answer, return receipt, or proven original requeue, it posts one visible overdue event and stops admitting repair turns. The owner keeps a six-hour due check of the exact receipt and return; a new answer or explicit recovery action resumes handling. A paused or unavailable asking session leaves the due obligation retained. Existing provider and peer ledgers remain the evidence for safe reconciliation; the reminder does not authorize resending.

When the asking session is paused, archived, or otherwise cannot receive the repair input, the owner records `external_hold` with the reason and its prior answer state, posts one visible hold event in the asking session when it exists, and keeps a due wake. Once that same session becomes messageable, the owner restores the prior state, posts a resume event, and admits the retained repair input. The hold does not consume or replace the original browser request.

## Peer and legacy boundaries

Each new peer request carries answer-guarantee version 1. A ChatGPT ask additionally carries its exact task and obligation claim. The recipient refuses an unversioned ChatGPT admission; the origin retains requests before network contact and holds an old peer acceptance that does not echo the version. It re-reads the original request ID after reconnection, without sending the request again. A peer worker's final has an exact request, recipient, target-session, and zero-unresolved-obligation proof. The origin requires that proof on the final, including a final pulled through status. Inferred work failure or stall also requires the receiver's versioned zero-unresolved count.

Startup classifies historical ChatGPT asks that can affect open work. An exact accepted source input equal to one open worker delivery input can link its old question to that task. The old answer still needs explicit handling; the migration does not dispatch an old browser input. A candidate task must have existed when the question was asked and still be open. A completed direct task or work admitted later to the same session cannot inherit an old question. Startup rechecks stored pending candidates against this rule and records a historical question with no surviving candidates as excluded from open work. Multiple surviving candidates, direct human tasks without explicit selection, and addressed peers without confirmed provider identity remain pending reconciliation and block candidate task closure. Unknown orphan membership cannot be assigned by time and requires an owner audit before activation.

After inspecting one pending row, the asking agent can use `sessions legacy-link <request-id> --for-task <exact-task> --provider chatgpt|other --reason <evidence>` from its current accepted run. The owner checks that the task is among the row's retained candidates and still belongs to that asking session. `chatgpt` links the original question and its retained attempt evidence; `other` classifies a peer recipient as non-ChatGPT and clears that false candidate hold. The command only changes owner records. It does not send or replay a browser input.

Source, build, installed server, and physical Mac evidence are separate. Each release report records which of these was actually checked.
