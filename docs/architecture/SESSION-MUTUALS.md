# Mutuals in session search

The owner derives session-to-Inbox-thread associations from accepted request receipts, using the current thread placement. Each distinct source message counts once for a receiving session in a thread. Failed requests do not count. Each event's contribution halves every 30 days; a thread's strength is capped at four. The projection reads the newest 5,000 relevant receipts per search, and returns topic identity, title, message count, last event and strength on each search result. There is no new persisted graph or writer.

Search retains its word/meaning reciprocal-rank fusion. The three strongest fused local candidates anchor a small co-occurrence lift for other matched local sessions that worked in the same thread. A thread shared by many candidates contributes less, so the busiest threads do not dominate. The lift is capped at 0.001; an association alone never adds a candidate. Peer-only receipts are not yet part of this projection. These weights are provisional; assess them against live ranking examples and latency before treating them as relevance evidence. thnkr.ing's explicit note-thread attachments remain at their owner and affect the session finder when searching inside that thread. See its [session mutuals](https://github.com/tejasdc/thinkering/blob/main/docs/architecture/session-mutuals.md) for the cross-owner contract.

The creating-event rule comes from Tejas's Circal social-calendar design: co-attendance creates a tie, while similarity does not.
