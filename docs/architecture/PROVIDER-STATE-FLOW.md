# Provider, account, work, and notice flow

This is the current operator map. [Provider sessions](PROVIDER-SESSIONS.md) owns model and execution details; [provider usage](PROVIDER-USAGE.md) owns allowance evidence; [session ownership](SESSION-OWNER.md) owns durable turns and requests. The [November 3 incident](../incidents/2026-11-03-withdrawn-mac-consult-usage-notice.md) is a replayable example.

## From a message to a provider

### Inbox provider continuity

The Inbox router is a durable logical role served by one agent session at a time. When every usable Claude account has exhausted its included allowance and Codex can start, the server owner proposes a Codex successor through the ordinary session handoff. The successor reads the prior conversation and accepts the exact inventory before the owner marks it as the Inbox router. Until acceptance, captures still go to the Claude predecessor. The handoff moves open requests, safe queued inputs and watches; it suspends the predecessor without interrupting a turn already admitted to Claude. Historical topic and message records keep their original session identity. Inbox topic lists and human reply reads include accepted handoff ancestors so old threads remain visible after takeover. This uses the existing handoff custody and acknowledgement boundary rather than a second router ledger.

The owner checks the router after its turns, on each fresh provider-usage reading, and when an Inbox session is requested. Exhausted usable allowance, or a queued router turn that cannot start before provider admission, proposes a handoff when the other coding provider has a usable route. A terminally failed input is not transferred by the handoff and cannot trigger it. The same rule works from Codex back to Claude once its allowance hold has ended. A proposed handoff is not a completed takeover; the successor's acceptance is the ownership transition. If the alternative cannot start or the inventory contains an input that may already have reached the old provider, the predecessor retains ownership so no ambiguous effect is replayed.

**Temporary November 5 Claude allowance hold.** Until 8 PM Eastern on November 5, 2026 (01:00 UTC November 6), the owner refuses creation of any new Claude session, including an explicit choice, and Automatic excludes Claude. Existing non-Inbox Claude sessions retain their accepted inputs, but their queued turns cannot be claimed; the queue wakes at the deadline to reconsider them. The current Inbox router's turns are exempt so capture and routing continue. The same hold refuses a fresh agent-started Claude command at the owner's launch-choice endpoint. A turn already running when this policy is installed is not canceled. The deadline ends the emergency hold; ordinary account and allowance checks still decide whether Claude can actually start.

1. The receiving owner records the exact input and its origin (human, agent, or service), request, session, and turn before a provider starts. The session keeps its selected provider and model. A turn does not silently change provider or model when an allowance runs out.
2. Claude Code, Codex, ChatGPT, and Antigravity are different executors. A Claude turn chooses an account on **the machine that owns that session** at dispatch. Claude homes keep credentials separate; an account with room but no working home on that machine is not an execution route. The selected account wins its next turn; a reusable warm prefix and allowance lapse pressure guide later choices among routes with room. A banked release is intentionally bound to the account whose window it saves. Codex's running App Server and Antigravity's CLI use their currently signed-in account; changing that login is a separate operation. ChatGPT uses its own account and capability path. No cross-provider fallback changes a session binding.
3. The owner asks the local worker to run the exact turn. It records the worker's effective account and the provider's execution identity. A running process is not interrupted or given another account simply because a reading changes.

### Claude Code started by an agent

A fresh Claude Code command started inside a Concierge agent's shell is another provider run, not a continuation of the caller's session. The agent's command path goes through the versioned Concierge launcher. Immediately before launch, that launcher asks the local session owner to choose from the same usable Claude account homes as an ordinary new turn, then asks Claude Code which subscription login it would actually use. A mismatch refuses the launch before the model request. When the owner refuses selection, the launcher reports the owner's reason, including an allowance hold, so the caller can distinguish it from an owner connection failure. The launcher does not change the caller's account or the machine's default Claude login. New account homes become eligible without restarting the calling agent.

The launcher resolves the installed Claude Code command before account selection. It skips Concierge wrappers from every release, including an older release retained in an agent shell's PATH; an immediate-parent guard refuses accidental wrapper recursion. If a package update temporarily removes the command or leaves a broken link, it watches the command directories and link target for up to two minutes, then continues as soon as the executable is usable. The observed November 4 installation took about 69 seconds; two minutes covers that measured operation while bounding a genuinely absent installation. The launcher reports when the command becomes available and how long it waited, or lists the checked paths on refusal. No model request is sent while the executable is unavailable. The [November 4 failure record](../incidents/2026-11-04-claude-command-install-gap.md) has the timestamp evidence and isolated replay.

An explicit account pin and a resumed or continued Claude conversation retain their existing credentials. An intentional API or cloud-provider credential needs an explicit pin; otherwise a competing credential refuses the automatic subscription route. Claude Code's built-in subagents belong to their running parent session and share its allowance; they are not independent account choices. The command path applies to agent shell invocations of `claude`; direct absolute executable paths are outside this command entrance and should not be used for fresh agent work. If the owner cannot answer, the launcher refuses instead of falling back to a default account that may be exhausted. A model request can still meet a limit after selection; a failed run with possible effects is not blindly replayed.

## What the allowance evidence means

- Each account and model has its own applicable windows. The provider's current five-hour, weekly, and model-specific windows are considered together. A full weekly window on one account says nothing about another account. A reset timestamp is attached to its account and window, never treated as a universal daily reset.
- A successful fresh reading may rank launchable accounts or predict a retry. An unreadable, stale, identity-mismatched, or failed reading is **unknown**, not exhausted and not zero use. If a proven login can run, an unknown reading permits a real provider attempt; only a fresh exhausted reading or an actual provider refusal can justify an allowance hold. A provider refusal's account, model, window, and reset are retained separately from the reader's snapshot.
- Anthropic documents [five-hour and weekly Claude limits](https://support.claude.com/en/articles/11647753-how-do-usage-and-length-limits-work) and account-specific weekly reset times. OpenAI's [Codex rate-limit response](https://github.com/openai/codex/blob/main/codex-rs/app-server-protocol/schema/json/v2/GetAccountRateLimitsResponse.json) and Google's [Gemini quotas](https://docs.cloud.google.com/gemini/docs/quotas) have their own scopes. Concierge cannot infer one provider's rules from another's.

## Wait, release, and withdrawal

- Only a live accepted turn can be held. A safe, confirmed zero-effect refusal leaves that same turn queued with its reason and next check. Uncertain execution stays explicit; it is never replayed from a guess. A hold's timestamp means **recheck eligibility**, not a promise that the provider will start at that instant.
- A fresh account reading, a newly usable local account, a verified top-up/reset, or the recorded reset deadline wakes held work. The owner chooses again at dispatch; it may move an ordinary Claude turn to another local home with room. Each machine discovers Claude accounts observed by its peer even when its own accounts read successfully, retaining the source time and treating the peer's account label as discovery rather than credential proof. A refresh with live usage-held work checks those discovered accounts for a missing local login and asks the browser repair agent to establish it. If a new account exists only on the server while the session lives on the Mac, its server capacity is visible but it cannot execute the Mac session until the Mac has its own proven login. The repair agent reaches Tejas only if his browser sign-in itself needs him. Account credentials are not copied between machines.
- Canceling an agent request durably records a revocation owed to its peer. The peer withdraws any unstarted target turn in the same transaction as closing that delivery, and withdraws the cancellation instruction when no worker ran. If delivery and cancellation cross in transit, the origin retries the revocation after the peer acknowledges acceptance. Reconciliation repairs older canceled deliveries that retained both turns. A running request follows the running cancellation path. Canceled turns remain in audit history but cannot be claimed at a reset.
- The session's receipt is the durable view of an accepted but unstarted message. A usage-held message must appear there with its hold reason. Provider history only shows work the provider actually received; it cannot prove a preflight queue is empty. Runnable, held, canceled, and historical inputs must be distinguished when counting a session's waiting work.

## Notices

- Account movement, temporary holds, allowance forecasts, and automatic reset-credit use are recorded for diagnosis and shown in Accounts or the affected session. They do not create a phone outage push or Needs attention item [decision: provider-account-notices-only-when-action-needed]. A raw internal agent consult is never described as “your message.”
- Concierge may ask Tejas to act when a real sign-in, explicit choice, or other decision only he can make blocks live work. That request names the affected work and the required action. A provider outage offer belongs to the specific live turn and must be rechecked before delivery; a withdrawn turn is ineligible.
- An accepted message's receipt remains visible while it waits and changes when it resumes, fails, or is withdrawn. A stale notice is not evidence that work is still waiting. The sender and display must check the authoritative turn and request state before making a current-state claim.

## November 3 example

At 2:27:39 PM ET a server agent sent an informational consult to Mac session 75. Its preflight found no Claude account with both room and a usable Mac home and queued the turn. The origin withdrew the consult at 2:27:48 PM. The old peer cancellation path closed the request but left that turn and a cancellation instruction in the Mac queue. The 2:28 PM notification presented the earlier hold as Tejas's message. The “3:00 AM” timestamp was the personal account's weekly reset, not the selected `tejas@chann.app` account's reset; `hey@tejas.nyc` had room on the server but no runnable Mac home. No Claude model request was attempted for that consult. The repair revokes both unstarted queue entries and prevents routine hold events from producing a phone outage.
