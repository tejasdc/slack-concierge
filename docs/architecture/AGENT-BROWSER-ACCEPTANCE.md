# Scoped agent browser acceptance

The private thnkr.ing browser bridge may read one real Concierge provider session created by an agent request. It does not use Tejas's sign-in. The bridge keeps the accepted agent source input and run, the exact `request:<uuid>` creation operation, and the returned `concierge:<id>` target in server-side startup configuration. It strips browser-supplied identity headers and injects `x-concierge-verified-agent-source: <input> <run>` and `x-concierge-agent-test-create: request:<uuid>` when it calls the private owner socket. Those headers are an assertion by the private bridge, not an Internet credential. On every call the owner checks the pair as the caller's current live run and the create request as retained lineage, as described under Current actor and creation lineage below.

The owner's `GET /sessions/v1/agent-test/sessions/<id>` family contains only `view`, `capabilities`, `receipts`, `receipts/changes`, `history`, `history/messages/<message>/detail`, `events`, `events/stream`, `operations/<operation>`, `attachments/<attachment>`, and `runs/<run>`. It returns the same body shapes and cursor semantics as the corresponding ordinary owner reads. The stream forces the target session filter and retains `Last-Event-ID`; an optional run filter narrows it further. Receipts use the prepared page and change positions. Operation IDs must belong to the target and have a source input in the creator session or the target session itself; attachment IDs must have a creator-session uploader and be named by an input of the target or uploaded by the caller's current run; run IDs must belong to the target. The session's own agent replies and requests remain visible because their source input belongs to that session. Any human input or input sourced by another agent closes this read entrance, preventing their words or provider response from becoming visible to the test browser.

For the same test, the bridge injects those two headers on `POST /sessions/v1/attachments` and `POST /sessions/v1/sessions/<id>/inputs`. The owner requires the body agent source to equal the verified pair, checks the input target against the creation operation, and requires each submitted attachment to belong to that source. The original unmarked human and agent paths keep their existing contract. The agent uses a stable action ID; duplicate writes retain one operation receipt. The command sequencer and its command-status endpoint are owned by thnkr.ing and must check the same target/source/action binding there.

The native Codex loss and Stop actions use the same private owner bridge and require a separate
explicitly marked disposable create input with a finite future fault deadline. Ordinary agent
creates do not acquire a dedicated client or fault controls. The owner binds controls to that
create request, its exact source input/run, and the target's current native run; it rechecks Stop
and the execution/attempt/connection generation immediately before a loss. Expiry disables only
loss injection: the normal Stop and recovery path keeps custody of accepted work. A callback or
bridge-disconnect acknowledgment does not prove provider termination; exact terminal provider
history does. See the wire contract and native Codex acceptance runbook for the retained receipt
and controller procedure.

This authorizes an acceptance entrance, not a fabricated provider turn. The requesting agent starts a disposable real provider session after both products have installed the contract, then observes the second browser's live session view, the accepted input and attachment receipts, provider delivery, and visible reply separately. A source build or owner unit check is not that observation.

## Current actor and creation lineage

The `x-concierge-verified-agent-source` pair (and a write's `agentSource`) is the caller's **current** admitted live run, the same check the Lab content guard makes of every agent read. It is not the creation pair: the run that created the test session usually ends, and a new run of the same creator session continues it. The immutable `x-concierge-agent-test-create` request stays the lineage. The owner takes the creator session from that create request's recorded source input and requires the current run's session to be that session; run or pair equality is not required. A header and a body that name different sources or create requests are refused (`AGENT_TEST_SCOPE_REFUSED`), and stop/loss controls take the one validated create ID as their authority and are creation-run only. Writes and controls additionally require a session that has not handed its work off. The authorship check accepts an agent input whose recorded source input belongs to the creator session or the test session itself; human, service (except the session's own pinned owner notice) and other-agent inputs still close the entrance. An attachment belongs to the test session when its uploader is the creator session and an input of the test session names it, or the caller's current run uploaded it for the input being written. Lab visibility is decided by the current run's own invocation, never by the creation run. A bridge is therefore started or rebound by the creator's current run with its own pair and the same create ID; an old bridge presenting an ended creation pair fails closed with `AGENT_SOURCE_REQUIRED`. The finite native Stop and connection-loss controls keep their old stricter binding: they accept only the run that created the test session (its exact create pair, still live), so a later creator run cannot renew their one-time allowance (`AGENT_TEST_SCOPE_REFUSED`). Ordinary reads and writes continue across creator runs.
