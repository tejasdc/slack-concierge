# Scoped agent browser acceptance

The private thnkr.ing browser bridge may read one real Concierge provider session created by an agent request. It does not use Tejas's sign-in. The bridge keeps the accepted agent source input and run, the exact `request:<uuid>` creation operation, and the returned `concierge:<id>` target in server-side startup configuration. It strips browser-supplied identity headers and injects `x-concierge-verified-agent-source: <input> <run>` and `x-concierge-agent-test-create: request:<uuid>` when it calls the private owner socket. Those headers are an assertion by the private bridge, not an Internet credential. The owner verifies them against its retained creation operation on every call.

The owner's `GET /sessions/v1/agent-test/sessions/<id>` family contains only `view`, `capabilities`, `receipts`, `receipts/changes`, `history`, `history/messages/<message>/detail`, `events`, `events/stream`, `operations/<operation>`, `attachments/<attachment>`, and `runs/<run>`. It returns the same body shapes and cursor semantics as the corresponding ordinary owner reads. The stream forces the target session filter and retains `Last-Event-ID`; an optional run filter narrows it further. Receipts use the prepared page and change positions. Operation IDs must belong to the target and source; attachment IDs must retain the source; run IDs must belong to the target. The session's own agent replies and requests remain visible because their source input belongs to that session. Any human input or input sourced by another agent closes this read entrance, preventing their words or provider response from becoming visible to the test browser.

For the same test, the bridge injects those two headers on `POST /sessions/v1/attachments` and `POST /sessions/v1/sessions/<id>/inputs`. The owner requires the body agent source to equal the verified pair, checks the input target against the creation operation, and requires each submitted attachment to belong to that source. The original unmarked human and agent paths keep their existing contract. The agent uses a stable action ID; duplicate writes retain one operation receipt. The command sequencer and its command-status endpoint are owned by thnkr.ing and must check the same target/source/action binding there.

This authorizes an acceptance entrance, not a fabricated provider turn. The requesting agent starts a disposable real provider session after both products have installed the contract, then observes the second browser's live session view, the accepted input and attachment receipts, provider delivery, and visible reply separately. A source build or owner unit check is not that observation.
