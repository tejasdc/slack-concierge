# External waits in the accepting owner

The accepting owner must yield while Git, GitHub, or the machine supervisor answers. A slow command may lengthen its own operation; it must not stop an unrelated session page, status read, or message. The command result returns to the existing operation owner. There is no second task queue or source of truth.

Project creation, sharing, and peer receipt use asynchronous child processes. Each project name has one in-process operation sequence, covering both local setup and incoming setup. The existing scaffold intent and exact private origin, remote HEAD, and local commit checks still precede creation records and peer orders. A process restart leaves the existing scaffold intent or receipt as the recovery point.

GitHub push acceptance has one operation sequence per deployment source. It fetches and checks the event commit, current main, and last known good commit before changing desired state. Ancestry answers for the current desired commit are gathered outside SQLite, rechecked if the desired commit changes while Git runs, then supplied to the existing synchronous transaction. No transaction awaits a child. Deployment reconciliation rechecks the desired commit after its Git commands before requesting an automatic deployment. Release history and status descriptions await Git reads in their own HTTP request; immutable title/range caches and fresh note reads keep their previous meanings.

Deployment runner and repair launch calls yield to the event loop. If a launch command has no usable answer and the supervisor cannot confirm a unit, the prepared deployment is retained for the next reconciliation; it is not marked as a failed launch. Execution host launch, supervisor inspection, and retirement also yield. A supervisor query that times out or fails remains `unknown`; only a definite refusal is `not started`. The existing execution and watch records retain intent before launch and custody after an ambiguous result.

This change covers the named accepting-owner paths, not every synchronous subprocess in the repository. The live Slack TODO projection still invokes Python synchronously for its atomic file exchange, and deprecated Canvas callbacks still invoke Git synchronously. Mac account/keychain and process-identity paths can also invoke synchronous OS commands. The deployment control programs, build checks, and CLI-only project migration paths run in separate processes; a source-level match in those files does not by itself prove an accepting-owner stall. The startup-only Git lookup in the owner runs before request acceptance.

Verification in an isolated scratch ledger used delayed fake Git and supervisor children. During 600 ms waits in project setup, push acceptance, and host launch, an independent owner status request finished before the child released. Two requests for the same project completed in order; a conflicting purpose was refused. Definite supervisor refusal and a lost supervisor answer retained distinct outcomes. This is source and isolated-behavior evidence only. Installed behavior requires the normal deployment and live check.
