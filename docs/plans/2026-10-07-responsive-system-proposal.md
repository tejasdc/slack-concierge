# A system that stays usable while agents work and services update

TL;DR: Today's failures are not one database problem. Expensive reads still occupy the same execution thread that receives messages; updates repeatedly disconnect that owner; provider and background processes have caused separate resource and lifecycle failures; and Mac dictation silently fell back to server processing. Replace those shared failure boundaries, retaining the existing conversation records and execution ownership. A wholesale rewrite or a different database, by itself, would not meet the requirement.

### Memory: a live recurrence establishes main-process attribution

At approximately 20:23, the host still had about 46 GiB available; Concierge used about 3.4 GB. By 20:33, its main Bun process alone had about 40 GiB of anonymous resident memory and tens of GiB swapped out. Filesystem cache in this service group was only about 0.3 MB. Host memory pressure stalled execution for about 41% of the preceding ten seconds. Both investigators read the process and group counters during this recurrence. The last ordinary memory timer at 20:29:28 reported 582 MB RSS; the timer then stopped reporting during the surge. This establishes rapid growth in the main process, not its allocation site or a JavaScript heap leak specifically.

Systemd records a client-requested kill at 20:33:18, not a kernel out-of-memory kill. This investigation did not kill or restart it. Another startup began at 20:33:36 and was followed by a planned deployment restart at 20:34:18. Recovery alone took about 39 seconds in the latter startup. At 20:36:23 the new owner reported 478 MB RSS. That low post-restart reading is not proof the cause is fixed. Peak memory and peak swap need not have occurred simultaneously. Historical process attribution remains unknown for the earlier 19:53 peak, but the new recurrence removes that uncertainty for this invocation.

The current group contains the owner, a roughly 1 GB search model, a roughly 1 GB speech model and a provider bridge. Provider executions now also occupy independent service groups, and a shared Codex daemon lives outside Concierge. A resource dashboard that omits those groups can falsely show an improvement after simply moving the work. Measure both per-owner and host-wide pressure. Do not add process RSS figures as unique physical memory. **No machine or service memory ceiling is selected:** Tejas's October 7 correction explicitly rejects that approach. The requirement is to identify and remove wasteful allocation while leaving legitimate work able to use the machine.

**Further recurrence during review:** at 20:51 Fable observed the next owner process above 40 GB, with its main loop thread consuming one core and small execution journals. At 20:52:33 Astra independently read PID1040905 RSS42,253,948 KiB and swap55,392,332 KiB, and group memory43,593,433,088 bytes. Its last recorded 25.4-second loop gap at 20:46:43 had no in-flight HTTP request, then logging stopped. That record does not prove no request began afterward, and main-thread CPU alone cannot distinguish JavaScript from native SQLite/JSC work. The allocation site remains unknown.

**Diagnostic correction:** the repair owner's newly committed warning says starting the in-process CPU profiler itself froze the owner for 20–40 seconds and preceded runaways. That correlation is not proof it allocated 40 GiB, but it invalidates treating the profiler as harmless or its timings as an unperturbed baseline. Before discovering that warning, Astra requested the documented SIGURG diagnostic during the already-established third surge. No completed profile was found afterward; that is not proof the signal had no effect. Astra did not restart or kill the service and will not request that profiler again. This was a miss in this investigation: the fresh diagnostic restriction should have been checked before using the old runbook. The repair source now refuses profiling by default (`8f61c14`); the observed running process was still the earlier `93b75bb`. Validate instrumentation in an isolated process before enabling it on a live owner. External process accounting remains the safe evidence source here.

### What changed today, and why it was insufficient

The owner-performance agent reports and supplies evidence for three morning defects: missing indexes in attribution lookups; an unfinished SQLite iterator leaving a stale read transaction which could not upgrade to a write; and checking whether a session could receive a message by building its entire presentation view. Those received targeted fixes. A new general index then caused the planner to scan an expensive ordering path; a narrower index and query correction restored responsiveness in the measured morning interval. That is a regression with an author and a mechanism, not proof that databases are intrinsically unreliable.

Later profiles again show large costs, now concentrated in rebuilding the set of open work receipts. Evening fixes removed unused full target-session views, added request lookups, adjusted shutdown and file-descriptor handling, and narrowed peer delivery reads. Their rollout is being verified by the incident owner. They are incident containment; they do not establish bounded cold reads, compact revision sync or independent human intake.

The execution-host design correctly separates provider-process lifetime from coordinator lifetime. Preserve that. The implementer identifies a narrower missed interaction: replay itself skips narration parsing, but leaves all replayed text in a buffer; every subsequent live chunk reparses that entire buffer. Independent source inspection and the pre-surge CPU profile confirm that path. Hosting lets runs live longer and adoption preloads megabytes, amplifying a pre-existing parser defect. It is a likely contributor to CPU saturation, **not an established explanation for 40 GiB retained memory**. Remove whole-output reparsing regardless of the allocation diagnosis.

The author reports replay itself below 200 ms in the measured 20:20 adoption, while journals here are 1–8 MB. That evidence argues against blaming full replay alone for the observed surge or claiming a committed cursor is the immediate repair. Streaming replay with bounded buffers is the smaller correction; compact recoverable state and committed positions are justified for a long-term recovery-time bound, with their consistency cost stated below.

The September cursor defect must not be misreported as current: the proxy's old 1,024-character ceiling is now 4,096. No current crossing is established. The deeper defects remain: the cursor lists all open receipts; a delta recomputes all of them; only a whole-history bootstrap earns that cursor; arbitrary delta failures still trigger full replacement; the notification reader has its own full-Inbox reconstruction.

## The required invariant

### What the feature authors missed

The continuation author on September 25 said: “I reviewed the diff for correctness only.” The per-row lookup and the loop calling it were both in that review; indexes, row counts and call frequency were not checked. The Threads author now says the invariant they protected was “the owner's lists are the truth and the app never recomputes”; they did not budget how often that truth was reread. Their current report confirms that every unrelated Inbox message refreshes the open thread, or every loaded list when no thread is open. A 600 ms debounce changes frequency, not the scope of the work. A five-second debounce would retain that architectural defect and merely make freshness worse.

The execution design author distinguishes native provider survival from loaded application recovery: their probes proved a provider survived losing a connection, not a coordinator recovering many executions, subscriptions and journals while a human sends a message. The observed 2.5-second historical restart was not an upper bound. The implementation author did exercise two real server restarts, adopting 93 and 130 frames, a background result after restart, and one helper reply delivered through downtime after nine seconds. Their admission is precise: “Every check used one short run” and none measured loaded CPU/RSS or composer/page performance. They deliberately skipped quadratic narration during replay but missed the replayed buffer's effect on subsequent live output.

The original inventory also missed live Mac speech's lifetime. On this Mac the installed execution-host launcher setting was empty, deliberately gated on uninstalled per-run hook wrappers requiring an administrator action. It was not a random missing setting and must not be enabled by bypassing that safety purpose. Code supporting hosts did not mean hosts were active there. Each machine and execution kind needs actual activation evidence, and any genuine device step must be named accurately when delivering that capability.

These are not failures to know that indexes or caching exist. Feature-local correctness, authority and isolated survival each passed while the cross-feature cost and lifetime contract was absent. The existing browser architecture checks remain useful, but cannot establish server work bounds or device lifecycle. The new architecture skill provides a sound method; it must demand a loaded recovery and growth experiment, and the release machinery must enforce the result. No instruction can make an unbounded API safe merely by telling its callers to be careful.

There are physical lower bounds: network round trips, storage writes, speech recognition and model reasoning take time. The enforceable product promise is immediate local feedback, prompt durable server acknowledgement under the supported load, bounded interactive reads, and honest progress during unavailable dependencies. “Everything is fixed forever” cannot be proved before implementation or against arbitrary failures. The release must demonstrate the named invariants, not merely get two models to agree.

## Proposed architecture

One person, two machines, several browser/native surfaces and many concurrent agents. No distributed database cluster, new message broker or internet-scale service mesh is justified by the evidence.

For example, opening a thread draws its saved recent messages, then reads that thread's small current page and changes. Another agent producing a long answer does not make this operation scan the Inbox or parse that agent's prior output. Sending a reply first saves it on the device and server, then the short command owner accepts it under the same identity and the agent picks it up through its existing queue. An unrelated server update does not restart the Mac's speech service. The page shows which of those steps is complete rather than leaving all of them behind “Sending.”

```text
Browser / native app
  saved drafts, recent pages, audio, outgoing action identities
       |                        |
       | small commands         | bounded page + changes
       v                        v
Stable intake and app gateway   Presentation reader
  durable transport custody      indexed prepared records
       |                        ^
       v                        |
Concierge command owner --------+
  accepted work, ordering, outcomes, revisions
       |                  |
       v                  v
Independent agent hosts   Bounded background workers
  provider lifetime         transcript import, search, reconstruction

Mac local speech -> editable words on Mac
saved audio -> custody upload independently
server speech fallback -> separate supervised job and result
```

### 1. A front door that stays open

Reuse the independently running capture ingress and its established durable-custody pattern for a narrow, typed human-command envelope. It is a transport inbox, not another session dispatcher. The browser retains the exact command and action identity before sending; the ingress authenticates, validates the envelope and persists it before acknowledging server custody. Only Concierge decides session semantics and records accepted work. On restart, the ingress delivers the same envelope; Concierge's unique command identity returns the existing acceptance rather than creating a second input. The ingress releases delivery responsibility only after that acknowledgement.

“Saved on this device”, “received by your server”, “accepted into this conversation” and “read by the agent” remain distinct. Offline capture can show the first immediately. A reply tied to an ended run cannot silently become a different command. Stop and cancellation keep their exact target identities; conflicting commands are ordered by the established owner. Attachments use retained references and their existing custody, not repeated embedded blobs.

The existing ingress database is separate from the coordinator ledger, so a busy coordinator writer or restart does not prevent the front door retaining a command. This is deliberately not a second source of session truth. The delivery protocol needs duplicate, lost-response and crash-before-ack checks. Sensitive control operations must retain the existing authorization and stale-target checks when applied; transport receipt does not pre-authorize them.

This delivery improves durability and truthful acknowledgement; it does not by itself reduce acceptance or agent-pickup latency. Those depend on the bounded command/observation work in §3. The current capture-delivery worker lives inside the coordinator and can be delayed with it. Its deployment hold must not apply to durable custody of human commands. After startup the command lane opens before background catalogue/subscription recovery; commands wait only for their exact required state to be reconciled, not for unrelated sessions.

All human session messages and ordered controls use one durable ingress sequence per client/session stream and carry their original action identity; the owner preserves accepted per-session order and deduplicates the same action if its reply was lost. Stop is an explicitly out-of-order control targeting the exact run, never “stop whatever is active when this eventually arrives.” A queued cancellation targets the original action identity and is effective before dispatch even if its message has not been imported yet. Agent/peer inputs retain the existing owner's ordering authority; ingress sequence does not pretend to impose a global order across machines. Recording bytes and all prerequisite custody must be retained before a command references them as server-held. A successful ingress receipt cannot mean only memory-buffered state; its database durability policy is part of the crash/power-loss acceptance case.

Why not just retry longer? Today's retry improves recovery but can make a person wait on the same blocked owner. Why not overlapping coordinators? That adds fencing and schema coexistence around effects without addressing expensive reads. A stable custody boundary buys the needed property with the existing intake mechanism. The app gateway itself still has maintenance outages; device custody covers those honestly, and its release must not restart merely because Concierge changes.

### 2. Replace presentation reconstruction with bounded reads

Keep SQLite as the authoritative ledger initially. Keep full original inputs, events and attachments for custody and audit. Add small, indexed presentation records for thread summaries, message pages, open obligations and receipt state. Large request/result bodies are fetched for the selected item, not repeated on a status poll. Every visible mutation updates its prepared record and a monotonic revision in the same transaction. A request answered in another session must advance every affected visible record's revision; this writer inventory is a prerequisite, not a later repair.

Cold open returns a bounded recent page with a revision, not the whole Inbox. A delta returns a bounded page of changed records and explicit deletions; clients drain further pages without throwing away their current view. A compact cursor identifies a collection/revision/snapshot epoch, not a growing list of unsettled requests. Expiry or a genuine gap produces a typed reset for the relevant bounded window. Authentication, validation, server failure and reset are different outcomes; none silently orders a full ledger download.

Snapshot and its revision have one consistency boundary. Pagination pins a defined high-water mark; updates while paging are subsequently caught by the change feed. A record removed from a visible window is distinguishable from permanent deletion. A client can retain a useful stale page while disconnected, but cannot claim it is fresh. Browser, native app, notification previews and agent readers use the same purpose-specific read contract. Full export remains an explicit background/export operation.

Events identify the changed topic/session and its new revision. Actions return the prepared records they changed. A message in another thread does not refresh the open thread, and marking one item read does not rehydrate every remembered list. Maintain sort/filter membership from the owner's bounded window-change contract rather than guessing membership from a partial row. Coalesce repeated changes to the same entity; do not put freshness on a blanket five-second delay.

The preparation work is bounded too: one input changes its indexed dependants, not every session's summary. A transition with unusually large fan-out records a durable projection job; its readers report the last applied revision until finite batches finish. It must not claim fresh state merely because canonical acceptance completed. Large rebuilds run off the interactive path. They build a new projection generation from a ledger snapshot, replay later revisions, verify consistency, then switch generation atomically; old clients receive a bounded reset. Original accepted work is never replaced by an old database backup.

#### Concrete data and synchronization contract

| Record | Stored shape and access path |
|---|---|
| Canonical input/operation | Exact identity, session, source, action identity, target/turn/request references; indexed foreign identities. Original bodies/attachments retain their existing custody. No new presentation store becomes the effect authority. |
| Prepared session/topic/message/receipt | Small typed fields needed for that view, exact canonical references, current revision; indexes match filter and keyset sort. Message bodies are separately versioned content references. No whole provider transcript embedded in a summary. |
| Presentation change | Unique monotonic sequence, collection/entity identity, change kind, bounded prepared value or immutable version reference; tombstone/membership removal explicit. Written with the canonical mutation and direct projection, or with a durable pending-projection fact. |
| Client checkpoint | Collection/window identity, projection epoch, applied sequence, cached rows. Rows and sequence persist atomically; the cursor does not list all unfinished work. |
| External observation | Exact provider/peer/session identity, observation version/time and freshness. The command owner applies received facts idempotently before advancing local presentation revisions. |

The isolated fixture used a mutable row revision to establish indexed selection. The complete protocol uses the bounded change records above so later updates cannot erase a change while a client drains a pinned high-water mark. A delta selects unique sequences after the checkpoint and up to that head, with a page/byte limit; another update gets a later sequence. Compaction retains the declared continuation horizon, and an older checkpoint receives a typed bounded reset. A single cold window and its head are read in one short transaction. Loading an older page starts another bounded snapshot and merges by identity/version; it does not keep a database transaction open while a person scrolls. The client applies subsequent changes to maintain its loaded window. This avoids promising a historical snapshot that the mutable-row fixture did not implement.

Mutation coverage is explicit. Acceptance/control writes update the operation and session; turn acknowledgement/hold/termination updates opening and steering inputs; a worker's late answer updates the requester's receipt and thread; sibling settlement updates every affected request; peer facts advance local revisions when received; thread moves update old and new roots; questions/read marks update topic membership and attention; attachment completion updates its metadata; streamed message versions preserve exact provider/message identity. Reverse indexes connect turn→inputs, request→source/target inputs, input→topic/root, and attachment→message references. Clock-driven holds/defer/expiry use their existing scheduler to write a transition; provider/peer reachability carries an observation version and freshness, never masquerades as a ledger-only fact. The implementation check must exercise every mutation family against rebuild-vs-live equivalence; an unknown writer is an acceptance failure.

Choose a **single mutation gateway with a release import/SQL boundary check**, rather than relying on an inventory staying current. All writes to receipt/summary dependencies go through registered commands in that gateway. Each command owns its transaction and declares the changed entity identities or a durable pending-projection job; domain modules cannot write those tables directly. The existing source architecture checker is extended to refuse raw mutation access elsewhere, including recovery/import helpers. Migrations use a separate offline/rebuild entrance and must rebuild or advance the epoch. SQLite triggers are the strongest alternative for detecting arbitrary table writes, but duplicating domain relationships and external observations inside SQL would add a second rule authority; they are not selected here. Fable found about 240 existing mutation statements across roughly 15 files, so moving every writer and proving equivalence is real migration work, not one more column. Review cannot accept a bypass marked “temporary.”

### 3. Protect the interactive execution thread

Separate the short command writer from CPU-heavy parsing, archive imports, search indexing, speech conversion and presentation reconstruction. Use a small bounded read/worker facility within the existing deployment ownership; separate read connections use WAL and short snapshots, while the mutation owner stays unique. Read transactions are finalized on every exit. No network/provider call occurs inside a write transaction. A busy read worker can fail or defer that read without holding message intake or Stop.

Provider observations are folded in finite batches with fairness toward human commands. Queues hold durable references, not unbounded copies of transcript bodies. A client disconnect cancels replaceable read work. Identical concurrent reads share work where safe; disconnected clients cannot accumulate limitless output buffers. A database timeout alone is not cancellation of synchronous work: isolation and bounded queries establish the actual boundary.

Each resource-heavy workload gets an owner, stop condition and a measured processing shape. Human commands receive fair scheduling ahead of replaceable background refreshes. Preserve already-admitted effects under pressure. Moving child processes alone cannot fix the observed 40 GiB growth in the coordinator itself: every expanding collection, result materialization and transport buffer needs an owning request/job, cancellation and disposal. Stream a large job without retaining all its intermediate copies. This is efficient data processing, not a ceiling on the machine's memory or a refusal to run useful work.

Concrete resource ownership: persisted prepared receipts replace the unbounded settled-receipt map; any optional memory cache has a byte-accounted working set and eviction that affects speed only. The per-run full-output string is replaced by the incremental reducer and bounded error tail. Replay frames use a bounded producer/consumer buffer with backpressure, not an array of the whole journal. Search and transcript readers stream limited pages; selected large content has a separate read path. The query/result byte budget includes text, not merely row count.

The initial review proposed supervisor memory ceilings. That candidate is **withdrawn**, following the correction retained in request `365bf65f-3787-4a83-98b6-bc62936c55f7` to the repair owner at 20:42:11: “Fix why the fuck it is going wrong” and “I want to fucking use the whole 64 JB if I want to.” The router acknowledged it had invented the ceiling instruction; commit `23fe1c7` removed it before installation. This proposal does not reintroduce it under another name. Resource tests must expose unexplained growth; they do not install runtime memory limits. Preserve accepted inputs and uncertain effects through any separately authorized incident recovery.

A low-volume external sampler belongs to this delivery: per-PID RSS/swap, group pressure, last request-start/finish and execution identity, plus inexpensive Bun heap/external counters when its loop can report them. It runs outside the measured owner so a blocked loop does not erase all evidence. The host uses both compressed-RAM and disk swap; swapping therefore consumes resources too. Keep request/job starts and ends, source sizes, collection cardinalities and growth under one operation identity without logging private text. Heap walks, CPU profilers and allocation instrumentation must first pass an isolated overhead/memory check; none is automatically invoked on the exhausted owner. Diagnostics have their own operational acceptance case. An external incident route must remain usable when the owner is blocked and an agent provider is out of allowance. Recorded process identity is already enough to name Bun as the culprit process; the missing allocation evidence is a logging defect that must be closed with the cause fix, not replaced by a list of guesses.

Account/provider health is another prepared observation: page reads return the last reading and its age while a background observer updates it. Opening or polling a page must not wait twice for a sleeping Mac. Preserve account authority and explain stale/unavailable observations; never imply cached health proves a fresh provider admission.

### 4. Finish restart recovery as an independent bounded operation

Keep the new independently supervised execution hosts. Host journals stream from a durable committed position, using segmented/indexed reads and transport backpressure. The acknowledgement position advances atomically with the durable projection it represents; a crash before that commit replays idempotently. Provider writes remain separately deduplicated and an ambiguous write is never blindly repeated. A compact recovery snapshot must include the policy facts needed to resume: pending input/write outcomes, task membership, clocks and provider identity. Merely saving a byte offset without that state would be incorrect.

Live provider output is reduced once, from newly completed protocol frames. Narration and final results derive from that same state; they do not repeatedly parse an ever-growing output string. The journal retains custody, while the coordinator holds only necessary current state and a bounded diagnostic tail. This directly addresses the measured parser amplification. Until a compact recovery snapshot passes equivalence and crash tests, stream full replay through an isolated fair worker with backpressure rather than invent a cursor that skips required policy facts. Neither path may replay an uncertain external effect.

Recovery snapshots have an explicit format and provider-adapter version. Extend the existing compatible/adoptable release inventory: first ship a reader that understands both formats, then emit the new format only when every allowed adopter and rollback target can read it. Keep the full audit journal; a snapshot is a derived acceleration, not authorization to truncate original evidence. Incompatibility is detected before activation and never “recovered” by rerunning the original request.

Adoption failure for one execution degrades that execution, not unrelated intake or page reads. Re-follow only live or explicitly requested provider sessions, not the entire historical catalogue at startup. Descriptor and process limits belong to the supervised provider daemon's launch configuration, with measured usage and cleanup; increasing a limit without bounding subscriptions only moves the failure point.

An optional/deprecated integration must not be able to terminate the native owner through an unhandled callback. Planned shutdown stops admission to effectful dispatch, releases owned resources and returns successfully; it is not labelled a crash. Compatible updates preserve inputs, working agents and read availability. Coalescing redundant updates may reduce churn, but a timer is not the architectural solution and must not delay an urgent repair or human command.

The delivery invariant is that an interactive listener does not restart for a component that did not change; if its owner must restart, retained commands/content remain usable and reconnection recovers by identity. Separate artifact dependencies and activation domains, rather than releasing every process on every commit. The existing `CONCIERGE_SLACK_ENABLED=0` configuration is a candidate containment measure for the deprecated client, after verifying native startup and no required remaining dependency; preserve its records. Suppressing a planned-shutdown exception alone does not isolate future optional-client failures.

### 5. Make Mac dictation actually independent

The implemented successful-local path already hands words to the field before uploading custody audio. Preserve it. The defect to resolve is local availability and fallback selection, not an assumed upload dependency in that successful path.

Give the local speech listener a stable supervised lifetime independent of frequent coordinator updates. At recording start retain the chosen engine/stream identity through finish; report probe, start, finalization and fallback reasons under the recording identity, without words. An unavailable probe must not masquerade as a successful local setup. Reuse saved chunks for a bounded local recovery when valid; no symptom-tuned extra waiting. If the local service is unavailable, retained audio and an explicit server fallback remain usable. The UI names the actual stages and machine rather than attributing every delay to a busy server.

The selected independent service includes a fresh capability probe at recording start and after a failed call; recovery must not depend on the browser later receiving focus. Capture starts into local custody immediately while availability is established. The recording retains its chosen stream identity even if global availability changes, and an explicit service-epoch mismatch selects a recorded recovery/fallback outcome. Giving the listener a separate process without this availability rule would retain the stale-flag defect.

On the server, speech runs as a separately supervised resource-bounded job. Input custody is acknowledged without keeping one long HTTP request open for conversion and recognition. Results arrive by the existing owner change channel; reconnect resumes observation by recording identity. Original audio remains recoverable even if recognition fails. Mac logs establish a restart at 20:13:48, during the first recording, and the Apple engine ready 40 ms after listeners opened. They contain no corresponding speech attempt/failure record for either clip. Record probe/start/append/finish/fallback under one clip identity before calling local dictation fixed.

Fable's subsequent read of the Mac log materially narrows this: there was no new successful probe until 20:22:52, after both clips; the next two local recordings finalized in 192 ms and 119 ms. The browser clears local availability after a failed call and normally re-probes on focus, so one disruption can leave later recordings on the server even after the listener returns. This is the strongest supported explanation for both clips: restart/disruption, unavailable state retained, then recovery on re-probe. The exact first failed local call is unlogged, so incident causality remains **likely**, while the restart, persistent-unavailable mechanism and later successful local timings are **confirmed**. The implementation author's speculation that server model loading explained the second clip is not supported by the measured conversion/recognition breakdown.

| Speech candidate | What it protects and what it costs |
|---|---|
| Existing listener plus re-probe at recording start/after failure, per-clip logging, and treating active recording as update-blocking work | Smallest containment; avoids some stale availability and mid-recording restarts. Still couples speech availability and update timing; long/repeated dictation can defer service updates. A successful start probe cannot protect a later restart by itself. |
| **Stable local speech service with that same probe/identity/diagnostic contract** | Selected for independent updates and sustained dictation. Adds one supervised lifetime but reuses the existing Apple engine/protocol and retained browser audio. Its own upgrades still require a speech-session handoff or waiting for that recording; unrelated Concierge updates do not. |
| Always server transcription | Simplifies local discovery but violates the requested on-device responsiveness and makes network/server health part of dictation. Not selected. |

Show the actual path and stage. Remove the unsupported generic explanation that every delay means “the server is busy.” A local failure must not be hidden by a successful but slow server fallback.

## What should refuse a regression

Priority is based on observed blast radius, not the order of boxes in the architecture:

| Priority | Complete protection | Cost and why it comes here |
|---|---|---|
| 1 | Bound interactive reads and streamed-output processing; enforce the mutation/read boundaries | Largest code/data migration, but directly addresses repeated measured CPU work and makes future features use safe primitives. More write work, indexes and derived storage replace repeated read reconstruction. |
| 2 | Remove unnecessary retained copies and unsafe instrumentation; independent resource diagnostics | Medium/high diagnostic work; preserves legitimate use of the whole machine. No memory ceilings. Allocation attribution and a non-growing loaded acceptance run are required before declaring the cause fixed. |
| 3 | Independent execution/speech/listener lifetimes and bounded compatible recovery | Medium/high protocol and cross-machine acceptance cost; prevents a routine update from becoming a shared outage. Retains useful host work and adds missing activation proof. |
| 4 | Independent durable human intake and complete command ordering | Medium/high custody/consumer work; protects a message when the page closes during an outage. Does not pretend to make an overloaded dispatcher fast. |
| 5 | Entity-specific refresh, shared cache/reset rules and fresh-enough health observations | Medium browser/native integration cost; removes needless repeated work while preserving canonical authority. Cache freshness and eviction remain explicit. |
| Across all | Candidate-release growth/restart checks and one actionable operational incident | Ongoing fixture/metric upkeep. This is what refuses recurrence; it is part of each complete capability, not a final optional clean-up. |

| Boundary | Enforced property and acceptance evidence |
|---|---|
| Read API | Required page/window, bounded rows and bytes; status reads cannot return retained prompt/result bodies. Every normal caller, including notifications, uses it. |
| Storage access | Query-count/rows-examined evidence for representative plans and growth fixtures; indexes tied to access paths. Do not ban every scan or require a brittle exact query-plan string. |
| Change feed | Mutating each visible source advances the right revision; duplicate/gap/reorder/restart/expiry/deletion cases converge without whole-history fallback. |
| Release | Real cold/warm thread open, send-to-durable-ack, notification preview and Mac voice checks; isolated restart/pressure/failure probes. Reject a measured regression against the baseline and acceptance budgets. |
| Runtime | Event-loop lag, queue age, per-process/group memory, pressure/swap, descriptors, worker backlog and degraded recovery have bounded-cardinality signals and one correlated incident. An agent investigates; alerts do not authorize blind restart loops. |
| Agent workflow | A short architecture entry declares data owner, read shape, write invalidation, lifetime and budget. The release check verifies them. More instruction prose alone is not the fix. |

Initial acceptance targets, **proposed rather than measured outcomes**: saved-page interaction/feedback within 100 ms; ordinary warm thread fresh data within 500 ms p95 on the named network; server-custody acknowledgement within 250 ms p95 once a request reaches healthy ingress; no multi-second main-loop task; device speech finalization measured separately from upload and server fallback. Cold opens, large attachments, remote peers and provider thinking have separate distributions and explicit reasons. Record worst cases as well as percentiles. Test with today's retained cardinalities and at least tenfold unrelated-history growth, plus the actual concurrent agent profile; a single quiet health request proves none of this.

### Checks run for this proposal

An isolated Python/SQLite fixture used the deployed receipt-selection query shape and its session index. With ten open records, increasing settled Inbox history from 1,000 to 100,000 rows increased the warm query median from 0.296 ms to 12.593 ms, although the result still contained ten rows. The plan sought the session index, evaluated the open-ID set and sorted temporary results. A synthetic indexed revision query returning no changes remained below 0.01 ms, and a 50-row page below 0.09 ms. Updating an old record and its revision in one transaction made the next delta return that late settlement in all nine cases.

This verifies a selection mechanism, not application latency. It omits receipt construction, payload size, browser work, network, write fan-out and competing agents; filesystem caches were uncontrolled. No production database or service was exercised by the fixture. The guarantee is an indexed seek plus bounded returned work, approximately O(log N + page), not literally constant cost at arbitrary history sizes. Pagination, deletion, reset and complete writer coverage still need implementation evidence.

Two additional bounded probes were run after Fable's challenge. With six synthetic live output frames, accumulated-output parsing rose from 1.51 ms total with 0.1 MB prior text to 65.27 ms with 8 MB; parsing only the new frames stayed below useful microbenchmark resolution. The isolated Bun process peaked at 111 MB RSS. This confirms growth, not the 40 GiB allocator. A throwaway inherited Unix listener on installed Bun1.4.2 worked through `node:net`, but the native HTTP server and HTTP compatibility interface ignored the supplied descriptor and opened another port. Therefore systemd socket ownership is not a drop-in HTTP fix here; a lower-level adapter would need its own contract and acceptance. No production listener or supervisor was changed.

Production investigation read both service journals, process/group/host pressure, provider/execution metadata, deployed source, retained CPU profiles, browser recording traces and the Mac's existing logs through its owner. It also requested one diagnostic signal, as disclosed above. The main-process memory surge was observed live. No allocation trace captured its onset. The retained CPU sample showed repeated Claude output parsing; source and an isolated probe establish the amplification defect. Because the profiler itself may perturb the service, its sampled distribution is not a natural-workload latency measurement. Retained output volume does not establish the 40 GiB allocator. Search recursion was checked and was not present in the inspected peer path. No heap dump or load test was run against the failing service.

### What future agents should learn automatically

The owning architecture skill should carry this specific incident and require four artifacts when adding a reader or lifetime: its growth variable and bounded access path; every writer that invalidates its data; the process that owns and stops it; and a loaded restart/growth acceptance case. A browser-performance skill alone cannot cover database plans or process lifetime. Keep one short project pointer to the reader registry and generated cost report; do not append another global manual.

The enforceable layer is a registry of typed reader/command contracts, a data-access boundary that refuses unpaged collection reads on interactive routes, and a candidate-release comparison against retained-cardinality fixtures. An agent should see a failing cost check with the exact reader and growth case, just as it sees a type error. Keep query plans as diagnostic evidence rather than brittle string assertions. These are proposed mechanisms; this investigation has not installed new instructions or enforcement. The skill lesson is secondary and must not be represented as prevention already delivered.

## Comparative decision

| Candidate | Where it wins | Where it fails or costs |
|---|---|---|
| Current architecture plus individual indexes/retries | Fast containment; preserve proven state | Does not bound reads, isolate resource pressure or keep intake independent. Repeated incidents demonstrate insufficiency. |
| Existing device outbox/retries plus owner action deduplication | Already provides retry safety and local draft preservation with fewer server components | A sleeping/closed client cannot finish upload during an owner outage. Does not keep owner acceptance fast under load; neither does an ingress receipt alone. Extend existing ingress for independent server custody, not as a claimed speed fix. |
| Supervisor-owned listening socket or listener handoff | A native supervisor can preserve a listening socket/backlog across process replacement | Installed Bun HTTP interfaces did not accept the inherited socket in our probe; only its lower-level network API did. Does not persist commands, keep established streams alive, bound stalled handlers or shorten recovery. Not selected as a substitute for data/work isolation. |
| **Rebuild read/sync, intake and resource boundaries while retaining the ledger and execution identities** | Directly addresses measured failure families; existing custody and host work remains useful | Significant migration and writer-coverage work; every entrance and consumer must be included. Recommended. |
| Replace SQLite with PostgreSQL | Native separate database process and broader concurrent workload capabilities | Does not prevent N+1 queries, whole-history payloads, loop-blocking JSON, failed local speech or provider restarts. Adds operations and migration. Reconsider if bounded SQLite workload still misses measured goals. |
| Adopt a maintained sync/workflow platform | Could replace custom protocol maintenance where a candidate meets exact semantics | No candidate has yet been shown to preserve all source identities, uncertain effects, offline peers and current provider contracts. Requires evaluation; not a proven immediate remedy. |
| Rewrite the entire application | Freedom to remove accumulated interfaces | Maximum custody/migration risk; can reproduce identical failure shapes. Justified only if a measured dependency audit shows boundaries cannot be replaced in place. No such proof yet. |
| Freeze/do nothing | Avoid fresh rollout churn | Leaves present failures. Not an acceptable resolution of the request. |

This is a substantial rebuild, not a promise that another index finishes it. It deliberately does not discard the data or correct execution ownership simply because adjacent components fail. Relative cost is lower than a full rewrite, but no honest calendar estimate exists until the mutation/consumer inventory and migration checks are complete.

## Delivery and recovery

The complete design covers all entrances and consumers; no partially supported feature is activated. Dependency-ordered whole deliveries can be reviewed and exercised separately: durable intake with its complete command contract; bounded presentation plus every consumer and its migration; worker/resource isolation; complete host-recovery protocol; local/server speech ownership. Each has a rollback that retains newly accepted work. These are complete capabilities, not half-features behind promises that later phases will make them safe.

Before implementing, publish the writer/consumer inventory and exact acceptance harness. On synthetic or copied state, establish growth, transaction and replay properties. On marked test executions, interrupt transport and coordinator ownership without touching real work. Once installed, exercise the same user-visible paths under representative background activity. Keep provenance for the artifact actually running. A successful build, process start or model review is not end-to-end acceptance.

The owning delivery team is Concierge for intake/mutations/read contracts/recovery, Thinkering for every browser/native/notification consumer and device custody, the Mac speech owner for the local lifetime, and remote-box for supervisor resource policy and external incident signals. One integrator owns the complete acceptance result; independent feature commits cannot each declare the shared surface healthy.

The acceptance harness runs an isolated candidate owner with a copied or generated representative ledger and stubbed external effects. It adopts six synthetic executions with up to the largest observed 8 MB journals and then streams another 10 MB across them, while a marked client opens cold/warm threads, sends commands, follows a notification and disconnects/reconnects. It records p50/p95/max for custody, owner acceptance, provider observation and paint separately; query work, bytes, queue age, CPU, RSS/swap and process identities accompany the trace. It crosses a coordinator restart while the browser closes, retries the same action, applies a late peer answer and reopens. No live provider effects or user state are replayed. This loaded restart/interaction harness is **specified but not run against an implementation**, because the replacement is not built. The three smaller experiments above are what was actually executed.

Once installed, a marked real client repeats those entrances while ordinary agents work, without killing unrelated user work. Mac local speech must complete during an unrelated coordinator update, and server fallback must retain audio and recover observation across reconnect. Verify installed launch configuration and hook compatibility on each machine. A true device permission/setup requirement is reported as such, never silently bypassed or mislabelled finished. Rollback changes code/read generation, never restores an old ledger over new accepted inputs. Keep compatible old readers until candidate generation and client migration are verified; then retire unrestricted interactive reads in that same complete capability delivery.

Failure cases required: connection lost before and after acknowledgement; duplicate command; stale target; a sleeping Mac; projection lag/gap; reader crash; writer lock; disk full; host exit after an uncertain effect; restart while speech finishes; cancellation racing completion; compatibility rollback; a slow client; and a background memory/descriptor consumer. The outcome must preserve the input and say which stage is pending or failed.
