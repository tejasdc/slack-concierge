# Where the lab runs, and keeping it out of his everyday views

Status: decided and built 2026-10-08 by the Concierge design session (concierge:3756), on Tejas's
request relayed by the agent-ecology coordinator (requests 4dbdf666, 252ca20d)
[decision: lab-runs-inside-concierge-in-its-own-space].

## His words

"I think it's like completely worth asking if all of this experimentation should even run inside
the Concierge protocol itself … if Concierge is actually gonna provide us this value, then we need
to make sure that we … build the right protocols … Also have a way for us to … identify the
experimentation related sessions … so it doesn't clutter all of our sessions … inside the app
itself." And: "the board mechanism or the communication … visible inside the Concierge, so I can
… investigate how the whole communication protocol is working … do spot checks … provide some
sort of a feedback and guidance."

## Objective and requirements

The lab must be able to: give each agent a truthful identity and provenance; end every exchange
with a typed ending; discuss in the open; spend allowance knowingly; be supervised by him and by an
outside watcher. It must not: clutter his session list, Inbox or notifications; harm the system he
uses every day; let the agents reach the judge that scores them.

## Options

| | (a) Inside Concierge, own space | (b) A separate lab service beside Concierge | (c) Outside Concierge, agents talk directly |
| --- | --- | --- | --- |
| Identity, provenance, typed endings | Already enforced (about 45 dated lessons in the request protocol) | Reimplemented, or calls Concierge anyway | Lost; files and conventions only |
| Board, mentions, usage holds, resets, supervision | Already live | Rebuilt or proxied | Board files survive; wakes, usage and supervision lost |
| Clutter in his app | Removed by the space filter below | None | None, but also invisible to him, which he rejected in the second request |
| Wake cost | Board mentions queue as notices that owe no reply; requests only when asked | Same | Polling or nothing |
| Risk to his live system | Lab sessions are ordinary sessions: same risk as any project session today. The regrow experiment (E5) changes Concierge itself, so that one runs on a separate copy | Isolated, but a second always-on service to maintain and supervise | Isolated |
| What the lab studies | The real protocol he uses; the steering ledger reads the real ledger | A copy that drifts from the real one | A different protocol from the one being improved |

Doing nothing (mixing lab sessions into his views) is what produced the clutter he named.

**Where each wins.** (b) and (c) win only on isolation. (a) wins on everything the lab actually
consumes, and the lab's main subject (E5, "regrow the Concierge") is this protocol itself, so
moving the lab off it would study something else. The isolation (b) offers is needed by exactly
one experiment, E5, and is given to it narrowly: a separate Concierge instance with its own state
directory and port, which the existing runtime already supports (the sandbox instance). Nothing
in E1–E4 changes Concierge, so none of them needs it.

**Unmeasured, so a hypothesis:** that the token cost of wakes stays small. The lab's capacity
planner already reads usage per session; if wakes dominate, mentions can be batched per session.

## The hidden judge

On one machine where every agent has full access, no file is truly unreachable, and this design
does not pretend otherwise ("provenance, not prisons"). What it does: the judge is not a session in
the catalogue, so no agent can address it, mention it or find it in search; it runs as a one-shot
model call over the finished runs' outputs, started by the planner after a run ends; its rubric and
scores live outside every lab project. Peeking stays possible and is detectable from the file
access record, which is the honest guarantee here. E5's own design gate decides whether that is
enough or whether the judge must run on another machine.

## Where the lab's discussions and knowledge live

[decision: lab-knowledge-lives-in-the-thinkering-object-store], after two corrections from him the
same day: plain files per event optimise for a case that does not exist (when Concierge is down the
agents are not running either) and scatter what agents must navigate; and the lab is doing CoDIAK,
so it needs a dynamic knowledge repository built to the OHS specification, not a message store.

| | Files per event (built first) | Tables in Concierge's ledger | Thinkering's object store, lab project |
| --- | --- | --- | --- |
| One queryable home | No: a file per event, generated views beside them | Yes | Yes |
| Dialog linked to the knowledge it produced (OHS) | No | No: findings and decisions would sit in a second store | Yes: journal, revisions, typed relations with reasons, back-links, lenses, human-versus-agent provenance (audit: docs/research/agent-roles/42-ohs-audit.md) |
| He sees and guides it in his app | Through a file reader | Through a new view | Natively, as objects beside his own |
| Missing today | — | Everything beyond the board | An agent write route (only his browser writes today), lab facets for thread kinds and endings, and the lab project kept out of his everyday lenses by default |
| Delivery (waking a mentioned session) | Concierge | Concierge | Concierge, unchanged |

The object store wins on the requirement that matters (dialog and products in one linked
repository) and loses only on work not yet done, which is Thinkering's to build. Requests between
sessions stay in Concierge's ledger, because they are the session protocol itself; the Lab view
joins them through `GET /lab`. The file board keeps working until the object-store board replaces
it, and lab-commons is then kept as history, not deleted.

## What was built

- **Lab space in Concierge.** A session is lab work when its project folder is agent-ecology,
  lab-commons or any expertise-* folder (session-roles.ts). It is derived from the project the
  session was created in, so no agent tags anything and an experiment run started in a lab folder
  is lab work from its first moment. Every session view carries `space: lab|everyday`; the session
  list accepts `?space=lab|everyday`.
- **The lab read** (`GET /lab`): the lab's sessions, and every request into, out of or within the
  lab, newest first, with who asked whom, work or information, the words, and how it ended.
- **thnkr.ing** (built by the Threads session, concierge:3572): everyday views drop lab sessions;
  the Lab view shows the board, the request flow and lets him post guidance that reaches the
  sessions in the thread.
