# Agent work, waking, and updates that do not wait for agents

**Recommendation — Proposed; confidence 88% in the separation, not yet a verified implementation.** Separate the lifetime of an execution from the lifetime of Concierge's coordinator. Keep one ledger and one active coordinator per machine; give each Claude streaming process (and each private Codex stdio process) an independently supervised, version-pinned execution host that keeps its pipes open and journals observations while the coordinator changes. Adopt existing shared-daemon Codex turns by their exact identities instead of declaring them interrupted when the coordinator dies. Replace the coordinator with a fenced, short handoff, with human intake continuing through the existing front door; never wait for all agent turns or hold human admission while building. Keep provider-native helpers and short background commands native. Add a small durable watch operation for work that must outlive a model run, using the existing ledger, service-input delivery and OS supervision. Do not turn a shell-text heuristic into the scheduler. This is a substantial lifecycle change, not a deployment-script tweak.

### Minimum proposed topology

```text
Thinkering / retained capture / peer input
                  |
      existing authenticated front door
                  |
       one active coordinator generation ---- one local ledger
                  |                             (intent, receipts, requests,
                  |                              cursor, results, watches)
       +----------+-------------------+
       |                              |
independent execution host     existing Codex daemon
       |                              |
Claude stream / private Codex   daemon-owned thread/turn
       |
native helpers and commands

OS-supervised durable watch --> existing service-input/outbox --> session
```

**Proposed:** run the same structure on each machine. Hosts are local, not remotely controlled general shell endpoints. The server owns work not tied to the Mac. The Mac owns its device/file watches and execution when physically needed; sleep pauses local progress, not server admission.

**Proposed:** an execution host is deliberately a transport custodian, not another Concierge. It starts one frozen launch manifest, owns pipes, spools framed provider events/stderr, accepts identified input/control commands and reports exact process exit. It does not choose providers, run the request coordinator, mutate session outcomes, schedule model work, parse prose as success or migrate the application ledger. It may keep a tiny journal separate from the ledger for transport custody; this is not a competing work queue. Provider-specific minimum control logic (stdin lifetime, result vs task membership, required protocol replies) must survive coordinator absence. Business decisions stay in the coordinator and are reconstructed by replay.

**Proposed:** OS supervision owns execution-host existence independently of the bot. Linux uses a per-execution service/cgroup with no `PartOf`/stop propagation from the coordinator. A `systemd-run --scope` or `nohup` change by itself is insufficient. macOS uses an independent launchd job/lifetime; exact launcher and permission attribution need a Mac acceptance check. Do not automatically restart an effectful provider after host death. The supervisor may recover the transport service only if it can prove it still owns the original child; otherwise retain an uncertain outcome.

**Proposed:** ordinary updates replace the HTTP owner, request coordinator, saved-work evaluator, projections and parser logic. Already-running hosts retain their old transport implementation; new hosts use the new release. Hosts need not be “never changed”: generations coexist behind a small versioned protocol. Provider executable upgrades and incompatible host-protocol changes affect only new runs until old executions finish; update status must distinguish coordinator installed from old executor generation still running. A critical defect inside an old host cannot be live-patched by this design; let that exact execution finish or take an explicit recovery action. Do not promise otherwise.

### Coordinator handoff and human priority

**Proposed:** build and preflight a candidate without holding admission. Keep the current coordinator serving while the candidate initializes without running schedulers or writing runtime ownership. Use the existing front door to route new connections to the candidate only after a transactional generation claim. Every provider-effect command, queue claim and request-worker claim checks that generation; every host rejects stale-controller commands. Fence the old coordinator before the new one can dispatch. Old handlers forward/retry the same accepted operation identity, never invent a replacement input. End old event streams with a reconnect cursor. Retain last-known-good and additive schema compatibility for rollback.

**Proposed:** during handoff, accepted human inputs remain durable and get priority over service returns, banked work and ordinary agent requests that have not been submitted. A message to a live run goes straight to native steering without waiting for the turn to end. Human messages must not be appended behind a large locally buffered agent backlog. Preserve ordering among human messages and retain displaced agent work; do not parallel-run two writers in the same provider conversation. A candidate failure routes back to the old compatible owner without stopping hosts.

**Likely, important limit:** “never wait” can mean no wait for an unrelated agent or update, and that is achievable. It cannot mean zero latency or preempting an indivisible provider tool call without interruption. If the provider's own queue cannot prioritize already-submitted messages, Concierge cannot reorder them retroactively. Keep nonhuman inputs in the owner until dispatch and disclose provider pickup truthfully. A separate urgent conversation is a deliberate product action, not silent duplicate execution. This distinction must be included in acceptance feedback; do not claim instant model response from an intake receipt.

**Proposed:** reuse the existing Thinkering server/capture boundary for durable intake and stable routing; do not add a third canonical input database. If the current direct owner socket has no stable handoff facility, a narrow socket broker or front-door routing change is required. Its only job is connection routing/retaining the same operation identity, not model dispatch. Strict zero dropped requests through socket replacement must be proven with a live reconnect check. A short transport handoff is qualitatively different from waiting an hour for an agent, but remains measured latency.

**Proposed:** ledger schema upgrades use expand/contract: add compatible fields first; old pinned helpers keep working; retire columns only after no live execution or rollback version needs them. A long exclusive migration cannot meet continuous intake; use compatible staged data conversion with bounded transactions. Never restore an old database backup over newly accepted work as application rollback.

**Proposed bootstrap limitation:** existing children cannot have their already-open pipes magically transferred to a new host. First install the ability to route/adopt hosted work while legacy runs are retained by their current owner; new executions then use hosts. For a currently unmodified legacy owner, the very first compatible runtime replacement still needs its natural finish boundary or a purpose-built legacy carrier handoff. Do not solve bootstrap by secretly killing it or restoring the global human-blocking gate. This one-time migration remains a delivery constraint, not evidence the steady-state design fails.

### Durable watch: yes, but a narrow operation

**Proposed:** Concierge should own a durable **obligation to observe and deliver an outcome**, not another arbitrary-agent runtime. Initial kinds should match real demand: a named project's file-condition watch and a named service/job status watch. A locally registered command observer is reasonable where a native subscription does not exist, but its executable, arguments, resource access and restart semantics are fixed by the integration, not free-form shell sent across peers. Avoid a generic remote `run this command for a day` API.

**Proposed lifecycle:** accepted → observing → fired / expired / failed / cancelled. Delivery is a separate pending → accepted state. Store origin authorization, canonical target session and binding policy, hosting machine, immutable condition, deadline, observed cursor/version, result and service-input identity. These fields respectively establish authority, destination, locality, meaning, end condition, restart continuity and deduplication. A repeating watch has explicit occurrence identity; never silently convert an edge watch into a schedule.

**Proposed example:** “Tell me when this report changes, for the next day.” Agent creates a file-version watch and finishes. Local worker saves baseline before acknowledgement, watches changes, rechecks state after reconnect/wake, retains the changed version and event in one transaction, then existing owner delivery wakes the same session. The session explains the change. A user message meanwhile runs normally. At deadline without a change, record expiry and deliver the requested end report. If the Mac slept, say when observation paused; a transient change that came and went during sleep is unknowable without a durable source log.

**Proposed guarantees:** level conditions are rechecked after subscription to close the setup race; event-only conditions need a replayable source cursor or explicitly weaker coverage. Watch workers acknowledge an event only after custody is durable. Restart read-only observers; never rerun an arbitrary effectful command after ambiguous exit. Disk exhaustion/backpressure stops claiming complete observation and produces a retained degraded state; do not silently drop events or kill the agent to free space. Retention follows delivered results and active cursors, with explicit handling if capacity runs out.

## C. Protocol and failure semantics

### Invariants

**Proposed:** one canonical session catalogue, one active coordinator generation per machine, one execution identity per admitted attempt, one provider submitter per execution, and one retained return identity per outcome. Transport disconnection changes observation state, not execution state. Provider completion, task exit, report delivery, report consumption and request completion are distinct facts. No time threshold or final-looking prose proves an effect succeeded.

### Local coordinator ↔ execution host

**Proposed service/environment:** reconnectable local transport custody over a private Unix socket; assume duplicated commands, lost replies, disconnected clients, partial journal tail, process death, PID reuse and version skew. Host paths are owner-derived from execution IDs. Only the local authorized owner can send commands; no peer-visible command/path slot. This is not isolation from another root process.

| Message | Minimal information and reason | Receiver rule |
|---|---|---|
| Start | Execution/attempt ID, immutable manifest digest, selected provider/account/cwd refs, coordinator generation, operation ID | One host instance lock per execution; acknowledge retained manifest before provider launch. Duplicate exact manifest returns same handle; conflict refuses. |
| Attach | Execution ID, generation, last committed event sequence, supported protocol versions | Verify host/process generation, fence stale writer, replay after cursor then stream live with no gap. Attach does not start or resume a new provider turn. |
| Submit/steer | Existing input ID, immutable bytes digest/content custody, command ID, generation | Journal custody before writing; same ID returns prior receipt. Record provider acknowledgement separately from pipe write. No blind resend after ambiguous write. |
| Stop | Exact execution/provider turn, command ID, generation | Retain intent and target; issue native interrupt once/reconcile; only terminal evidence confirms stopped. Never cancel the next run. |
| Observation | Execution ID, monotonic sequence, typed/raw provider payload, provider IDs/time when available | Append before publication. Coordinator writes projection and cursor atomically. Duplicate sequence is harmless. |
| Status/terminal | Exact process identity, last sequence, pending commands, provider result/exit evidence | Distinguish process exit from successful model result, and live/unreachable from dead. Retain terminal until coordinator acknowledges custody. |

**Proposed host states:** prepared → starting → live → exited; ambiguous launch/write is retained as such, not automatically retried. Attached/detached is an orthogonal connection state. **Proposed coordinator states:** intent retained → host custody → provider admitted/acknowledged → result retained → settled; adoption changes controller generation without incrementing dispatch attempt or clearing acknowledgement. Before launch, an owner-derived lock and host manifest prevent two processes from starting the same execution; a crash after spawn but before PID retention still requires process-identity evidence, not a second launch.

**Proposed:** replace the conflation of `turns.owner_instance_id` with two concepts: execution custodian and coordinator claim generation. Keep `process_instances` kernel identity checks. Heartbeat absence alone cannot prove death on a sleeping Mac. All existing guarded settlement, steering and request-source validation must accept the adopted run under the new coordinator without changing its public run/input IDs. Rehydrate active registry before queue promotion, so the same session cannot receive a second overlapping execution.

**Proposed:** host spools framed provider records before notifying the coordinator; its event sequence and execution ID are the dedup key. Acknowledged projection cursor advances in the same ledger transaction as projection effects/outbox writes. Replayed output is observation only. Transcript UUIDs corroborate input pickup; missing pickup is not proof input was never read. Preserve raw stream/transcript evidence for reconciliation, but avoid logs containing secrets. A torn final record is distinguishable from a complete event.

**Unknown/hard limit:** there is no atomic transaction spanning SQLite, OS pipe write and an arbitrary provider's tools. Host death between pipe write and durable acknowledgement can remain ambiguous; a remote side effect can succeed just before local evidence is lost. Stable identities make retries safe only where the receiving operation actually deduplicates them. The promised property is no blind duplicate and no discarded accepted obligation, not universal exactly-once external effects under arbitrary machine failure. Ordinary coordinator update can avoid this ambiguity because its custodian stays alive.

### Provider-native task observation, without rebuilding delegation

**Confirmed defect in current adapter:** the SDK says `background_tasks_changed` is a complete replacement set and provides descriptions/ambient flags (`sdk.d.ts:3395`). Current code uses it only to notice removals (`claude-code.ts:685`); it does not add jobs missing a `task_started` edge. Its edge handler also ignores only `ambient` starts, without applying later ambient transitions. **Likely consequence:** a missed start or reconnect snapshot cannot rebuild task membership correctly. The current two-minute path depends on first having observed a task; it is not a complete reconciliation backstop.

**Proposed:** fold level snapshots as authoritative membership for that provider process generation; retain separate task-ended, report-delivered and report-consumed evidence. A task absent from a snapshot is no longer live, but absence alone does not prove success. At reconnect request supported snapshot/reinitialize behavior; the local SDK explicitly documents a snapshot behind repeated initialize for newer CLIs, absent on older ones. Never turn that capability into an assumed guarantee for every installed version. If no native query exists, expose unknown and reconcile from retained task output, not invented completion.

**Proposed:** preserve Claude's native completion delivery first. If completion is confirmed but delivery is missing, emit one idempotent recovery notice with the exact output reference/status. If native delivery later arrives, merge its evidence rather than starting another top-level model turn. The owner should use observed notification origin/UUID and provider task ID, not prose similarity. Codex native child completion remains its own mailbox; Concierge adds only oversight/durable-session obligations the native lifecycle cannot promise.

### Existing requests and established models

**Confirmed:** Concierge already uses explicit request replies and retained return inputs. Keep that FIPA-style separation of acceptance and result, plus current partial/failed/needs-decision semantics. No new protocol for helper result text is needed. The canonical FIPA website could not be fetched in this investigation; the mapping is supported by the existing project design (`request-reply-protocol.md:35–59`), not a claimed new external verification.

**Proposed, grounded analogy:** OS supervisors resemble Erlang supervision trees: independent failures have independent restart decisions; restarting the coordinator should not terminate execution siblings. But effectful workers must not receive unconditional restart policies merely because Erlang supports them. [Erlang supervision](https://www.erlang.org/doc/system/sup_princ.html).

**Proposed, grounded analogy:** use Temporal's distinction between durable workflow state and signals: a watch's result can reach a sleeping logical session without a model process waiting. Use its recovery principle, not deterministic replay of LLM/shell execution. Existing SQLite intent/outbox is sufficient here; adopting Temporal would add a service and migration without demonstrated need. [Workflow execution](https://docs.temporal.io/workflows), [signals and messages](https://docs.temporal.io/encyclopedia/workflow-message-passing).

**Proposed:** actor-mailbox ordering fits sessions, but logical serialization does not require holding the physical HTTP coordinator alive. Prioritize human inputs before nonhuman dispatch, retain exact order/identity, and let accepted cross-machine messages remain in the existing peer outbox while the Mac sleeps. Do not build a second peer watch transport or treat sleeping as failure.

### Failure matrix

| Failure | Proposed invariant-preserving outcome |
|---|---|
| Coordinator restarts during provider output | Host keeps reading; new owner replays from committed cursor; same run remains active. |
| Coordinator dies after input accepted, before submit | Durable intent is picked up once; host command identity prevents duplicate launch/write where custody already exists. |
| Host receives command but response is lost | Retry same operation ID; inspect retained receipt. Do not equate timeout with refusal. |
| Host dies after ambiguous provider write | Reconcile exact transcript/provider IDs; retain uncertainty if unresolved, never repeat the original task automatically. |
| Two coordinators overlap | Ledger generation fence plus host writer fence rejects stale effects; observer duplicates deduplicate. |
| Old coordinator request races handoff | Transaction either belongs to old valid generation or retries with same identity at new owner; no new input alias. |
| Native task report is lost | Reconcile native state/output; one recovery input, late native report merged. |
| Native task start edge is lost | Full membership snapshot rebuilds observed tasks; no dependence on paired edge events. |
| Codex connection lost with approval/dynamic tool pending | Reconcile pending native request and exact policy; cannot assume disconnected client obligation is preserved. Never approve a new action from an old RPC ID. |
| Mac sleeps/reboots | Sleep pauses local observer; wake reconciles. Reboot ends live compute; prove result or retain uncertainty. Server work continues. |
| Application rollback | Reattach surviving execution generation using compatible protocol/schema; retain all newly accepted inputs. |
| Old release cleanup | Refuse removal while any live host or pinned helper manifest references it. |
| Watch fires while session paused/archived | Retain result and pending delivery; honor existing session hold, show recorded outcome, do not force a model run. |
| Human Stop races result | Record exact Stop intent; terminal/result evidence determines outcome; do not rewrite completed effects as cancelled. |

## D. Per-command checks: bounded and cheap

**Confirmed:** this is a Concierge-supplied hook invoked by the provider, not a model capability or SQLite loop. Claude receives settings at launch (`claude-code.ts:398–405`). Codex receives managed PreToolUse/Stop definitions, with no PreToolUse matcher in this installer (`install-codex-stop-hook.sh:85–105`), so coverage is broader than just shell calls. Claude's launch matcher also includes file-reading tools and navigation, beyond the brief's list. A separate machine settings entry may overlap; actual provider deduplication/duplicate invocation was not measured.

**Confirmed:** current guard does more than the brief lists: direct Messages/notification database read refusal and audit, waiter checks, self-matching process waits, pushed-history checks, shared-checkout writable Codex launch refusal, and website runbook context (`history-guard.ts:92–122`). It is already accumulating unrelated responsibilities.

**Confirmed measurement:** 30 warm sequential no-op subprocess invocations on this Mac, one warmup excluded, using Python `perf_counter` around subprocess creation/completion:

| Command | Median | p95 sample | Maximum |
|---|---:|---:|---:|
| Installed Bun `-e ''` | 4.33 ms | 5.23 ms | 5.73 ms |
| Source `history-guard.ts`, Bash `true` JSON | 20.35 ms | 22.72 ms | 23.27 ms |

**Unknown:** production compiled-bundle cost, cold start, server cost, duplicated hooks, provider scheduling overhead and real p99. This measurement is not a latency guarantee. Thirty invocations launched no real tool command and generated no denial/audit record. At this measured median, 1,000 sequential invocations add roughly 20 seconds cumulatively, not 20 seconds to every response.

**Confirmed:** Git amend/rebase checks can enumerate remotes and run `ls-remote` with 8-second per-command timeout, then Git ancestry queries (`history-guard.ts:45–83`). Thus the expensive path is not bounded solely by the small pure-check count; remote count and ancestry checks also matter. Whole hook timeout is 20 seconds. Broad exception handling lets unexpected errors through (`:111`); the hook is not an absolute security boundary.

**Confirmed:** wait-only detection splits shell strings and checks an allowlist including `sleep`, `cat`, `tail`, `grep` and tests (`background-waiter-policy.ts:20–57`). It does not inspect file provenance or the job graph. A legitimate `while ...; sleep ...` file watch can be refused. A `python` wrapper or `rg` version may pass. The claim that this knows it is waiting on its own helper is unsupported. An unfamiliar command is intentionally allowed, so this is not an enforcement boundary for background lifecycle.

**Proposed comparative decision:** remove hard wait-only refusal from the generic pre-command path once native lifecycle observation and durable-watch routing are delivered together. Retain a concise advisory for clearly redundant native-helper polling if useful, evaluated once per job rather than every command. Stream handling is the right place to observe actual task IDs, state and duration; it is too late to prevent an already-launched command, so do not pretend a stream warning is a preflight guarantee. Moving the same shell heuristic into the parser would retain its false positives without fixing ownership. Doing nothing preserves false refusals; growing the allowlist creates an unmaintainable shell classifier. Native completion + durable watches removes the need for the classification entirely.

**Proposed bounded design:** keep one small hook entrypoint with a cheap tool/operation discriminator. Only irreversible or sensitive operations that must be refused before effects belong there: protected data access and specific destructive history operations, with upstream OS/Git policy as the authoritative backstop where possible. Writable delegation placement belongs at delegation launch; owed replies belong at Stop/request API; background liveness belongs at task owner; website advice belongs at navigation entry. No network call, ledger open or repository traversal on unrelated commands. Measure cold/warm costs per dispatched policy; make a growth check require each new policy to name the irreversible effect and why its actual operation boundary cannot enforce it. Bound remote/history inspection with one total deadline and an explicit indeterminate result; do not pretend cached refs alone prove nothing was pushed. No permanent hook daemon is justified by a 20 ms no-op measurement alone.
