## Decision case

Doing nothing leaves saved reasons without an accountable actor. Expanding the keeper prompt alone still permits storage-only success. Sending every journal entry to Inbox creates unwanted threads and promotes reflection into work. A separate classifier or queue duplicates the existing keeper and delivery machinery.

Reuse the keeper for semantic judgment, the canonical saved-word queue for coverage, and existing Inbox report/request machinery for actionable portions. Add a typed processing receipt and completion check. The check enforces a recorded judgment and real handoff; it cannot prove a model's interpretation is correct. Exact source quotes and retained reasons make that judgment inspectable.

## Whole delivery

1. Thinkering's canonical saved-word watcher covers check-in roots from every save entrance, with the existing root-and-word job identity and recovery. Existing escape costs and rules stay intact. The private source reader adds revision and actor evidence without removing old fields.
2. New Concierge keeper admissions carry a typed journal-processing obligation. Existing admitted inputs remain unchanged. Service authorship stays service authorship.
3. A structured journal review records either context-only with its reason or exact quoted actionable portions, distinguishing an explicit request from a reason requiring assessment. The private canonical source validates each quoted line and retains its revision, original time and actor. Agent/imported text does not silently become human authority.
4. Actionable portions create or link durable Inbox requests before routing. Their identity follows source root, line and exact quote across reviewing runs and word versions. Retries return the same admitted work; an unknown execution state is never a reason to replay it. Distinct portions retain distinct obligations.
5. A new keeper input cannot report successful processing with tracker observations alone. The outcome/stop boundary requires the structured review receipt. This is an agent processing claim, never a new field or permission step for the person writing: saving, journal access and tracker filing continue independently. Delivery, review, routing and final action outcome remain different facts. Explicit processing failure remains inspectable.
6. Inbox routes each actionable portion to its appropriate continuing agent. The friction actor evaluates the requested exception against deliberate rules and current context; this change grants no blanket friction bypass. Existing request returns carry results to the relevant Inbox thread. Ordinary reflections create no work thread.

## State card

- Entity/writer: Thinkering alone owns saved journal words and queue jobs. Concierge alone owns admitted inputs, review receipts, Inbox requests and routing.
- Identity: existing root/word job ID for delivery; source-root/line/quote identity for an actionable portion, independent of reviewing run.
- Acceptance ladder: saved words -> durable delivery job -> keeper admission -> source-bound classification -> Inbox obligation -> receiving agent's accepted work -> explicit outcome visible in its thread. None substitutes for the next rung.
- Provisional state: queued/delivered is not processed. An unreviewed new keeper input remains owed. An actionable item retains its open request until the actual actor returns.
- Lifetime: existing canonical queue survives app restart; Concierge persists accepted inputs and receipts; this coordinator runs outside Concierge. No file watcher or new lifetime is added.
- Old readers: additive source metadata; missing revision/actor proof refuses an actionable claim. Existing admitted service inputs have no retroactive processing gate. Existing delivered jobs are not replayed merely to acquire the new receipt.
- Failure trace: saved reason -> durable Inbox report accepted -> response lost -> retry by stable source identity -> original request and attribution returned, no second effect.
- Falsifying sequence: tracker-only success on a newly admitted source must fail; context-only review creates no Inbox topic; two actionable portions create two tracked requests; retry after report acceptance creates none.
