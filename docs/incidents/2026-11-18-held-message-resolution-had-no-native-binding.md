# Held message resolution lost its native return address

## What was seen

Request bbb4bc17-a464-43ef-a6c2-4400770bac6e follows contract consultation
4cce0580-25c6-4a00-ae0e-f4715ec4acd4. The product scheduler retained an assigned
send task and failed reading, but no current agent input/run authority. Generic
feature admission retained only service text and a self-sourced identity; normal
worker-question filing required the exact dispatched target input.

## Cause

The product service event was neither a new human instruction nor an active agent
request. Generic admission lacked an owner-proven original dispatch/thread edge.
Borrowing a historical run or using human input would falsify authority. Prior
owner9884 also identified that a self-sourced feature input using a real target run
could accidentally qualify for the pinned-owner-notice authorship exemption.

## Fix

Extend feature admission with one typed resolution, derived from the original
assigned input by the native owner. Retain service authorship, original human
lineage, informational scope, thread and immutable service evidence references.
Require a separate owner event plus accepted input before projecting provenance
or filing questions. Reuse the native queue/receipts and recheck Stop/custody.
The foreign-authorship predicate remains unchanged.

## Acceptance scenario

- **Seed:** An admitted local Inbox-routed messaging request, unchanged human
  source/thread, product-held task and exact retained failed-reading hash.
- **Action:** Submit one bound service resolution; repeat it; change its binding.
  Its assigned worker asks a genuine human-only question through normal outcome.
  Separate cases stop, cancel, pause, archive or hand off before admission/dispatch.
- **Expected:** One service operation and original human/informational provenance;
  same duplicate receipt; changed-content refusal; question in original thread.
  Fenced work cannot execute. No new send, test push or manufactured human question.
- **Replayable offline:** yes (isolated native owner/ledger composition; product
  byte freshness and physical device display require product-owned acceptance).


## Caller custody clarification before first release

The product owner confirmed that retained task operations may use a bare native
communication UUID and that a direct-human operation is also possible. Resolve
only owner-proven request aliases; refuse the direct-human shape explicitly in
this release. Historical Rohan examples are already sent and must not be invoked.
The product owner supplies a trusted, side-effect-free pending-resolution read;
native admission checks current task/message/source/reading/envelope identity,
verifies exact diagnostic bytes, then rechecks native custody before its write.
Repair/model failures cannot become a native human question through this binding.
