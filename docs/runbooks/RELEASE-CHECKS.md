# Bounded release checks

The required GitHub result remains **Release check**. Independent GitHub-hosted jobs run the package and native history-cache groups at one immutable source revision. The final result runs even after failure or cancellation and requires group selection and every matrix member to succeed at that exact revision. Failure, cancellation, skipping, a missing result or a missing/mismatched source identity cannot produce success. Failure-record checks, frozen dependencies and the cancellation regression remain required. Restic and Bubblewrap are installed before checks. Every original command remains mandatory on every release; no check moved to another cadence.

`bot/scripts/release-checks.json` owns both command groups. CI derives its matrix through `bun run scripts/run-release-checks.ts --matrix`; it keeps no second group list. The undefined-name guard derives bundle entrypoints from the same inventory. `bot/scripts/release-check-policy.json` owns each group’s execution budget and parallelism. Package `bun run build` selects the build group; explicit selectors are `--group build` and `--group historyCache`. The compatible `--history-cache` alias remains accepted. The former combined `--ci` mode is refused because it cannot promise one bounded group for both workloads.

Each suite has 120 seconds including a five-second cleanup allowance. The supervisor grants at most 115 seconds to the complete check tree and then stops its owned group and awaits complete native group cleanup within the remaining allowance. A failure cancels other active commands and prevents successful compilation or a green result with unexecuted checks. Cleanup that cannot be confirmed is a failure, never successful completion. Diagnostics retain full per-command stdout, stderr, command, result, and duration beneath the reported scratch path.

Three independent command lanes overlap existing waits on the same CI runner. Every command gets a distinct scratch state and capture directory. An exact nested private-code command keeps its existing test-mode and explicit scratch database environment while reusing the root's already verified isolation; it does not create redundant user namespaces. Ordinary inventory commands retain their own environment contract. Package compilation runs only after every check in its build group passes; the independent history group must also pass before the final required result. The final bundle output remains an acceptance artifact, separate from a sealed or installed release. The candidate-owned presentation entrance has its own identical total budget, so an older controller executing that entrance also receives bounded failure rather than an unbounded child wait.

The process boundary matters: the outer check owns one kernel process group, and nested fixture helpers inherit it. They do not create detached groups outside the outer cancellation. Only the owning root certifies native group cleanup; a nested result explicitly covers its directly owned leader under parent group custody. Known native lifetimes use pidfd readiness through the existing Python dependency, rather than treating a zombie leader as complete. Lifecycle fixtures retain their final checkpoints and assertions. The cancellation regression runs as a separate CI step so it can observe a killed group from outside it. It holds a nested child and inherited pipe and asserts descendant cleanup at return. GNU hard-kill is a failed, uncertain result without a successful cleanup receipt; it never creates a passing result.

The named native-group fixture follows that same boundary: inside the suite it verifies spawn failures and the directly owned native process/thread lifetime while retaining the enclosing group, and reports `leader-under-parent-group` custody without claiming group completion. Its standalone invocation keeps the complete owned-group proof, including no identity/spawn notification for missing or non-executable commands. The existing outside-group CI cancellation/cleanup step also runs that standalone invocation through the private-code entrance with `--require-owned-group`, so full-group coverage recurs and refuses an inherited-group downgrade without escaping the bounded suite's group or weakening its ownership guard.

The database-safety overlay is disposable mount/read/mask acceptance, with explicit
native unmount and group cleanup. It uses the kernel's `volatile` OverlayFS mode:
default overlay synchronization can synchronize the entire upper filesystem, so a
throwaway mount check would otherwise depend on unrelated disk writeback during
cleanup. This native mode omits upper-filesystem synchronization and gives up crash
survival for that owned scratch overlay. Its contents are recreated and discarded;
no application ledger, backup or durability receipt uses this option. The existing
`nosymfollow`, protected directory/backing masks, overlay readback, direct `umount2`
and complete native cleanup assertions remain required. Neither a longer deadline
nor reduced concurrency substitutes for those assertions.
[Linux OverlayFS contract](https://docs.kernel.org/filesystems/overlayfs.html#volatile-mount).

Reproduce the package check with `cd bot && bun run build`. For all CI coverage locally, install the existing Restic dependency and run the package check, then `cd bot && bun run scripts/run-release-checks.ts --group historyCache` sequentially as separate bounded groups. GitHub uses independent ephemeral runners; this changes no concurrency or resource allocation on the server or laptop. CI queueing, setup time and additional runner cost are unmeasured, and total workflow time is not claimed to fit one group budget. Run the cancellation regression with `bun bot/scripts/release-check-lifetime-fixture.ts`. The Linux private-code entrance verifies the inherited database directory and loop-backing masks before importing application code. Its outer namespace also hides the real Codex home, removes inherited shared-server selectors, gives children a private PID namespace, and replaces systemctl, systemd-run, prlimit and busctl with refusing executables. HOME keeps its original value. Fixture-owned endpoints and controlled executable overlays may be selected only after that independent boundary is verified. The outer group guardian stays outside the PID namespace and owns cancellation through native cleanup. HOME child rebinds precede the final database/backing masks; the owned-sentinel regression proves that reversing this order uncovers the scratch topology. Permission to traverse an empty root-owned mask is not evidence of access to the underlying data.

This private verification entrance now refuses on non-Linux hosts instead of passing checks through without its isolation contract. This changes only private verification; ordinary Mac commands and runtime behavior are unchanged. Server acceptance uses this Linux entrance. The guard protects canonical ledger and shared Codex lifecycle/data boundaries; it is not a claim to isolate all provider credentials or arbitrary network traffic. The existing history-growth check still attempts its unmocked startup connection; a swallowed connection error and successful local history page are not real-provider acceptance. The dedicated page-worker regression separately compiles a daemon collaborator into both parent and worker, then verifies the independent barriers inside the child before imports.

Disposable development measurements were 105.7 seconds for the held WAL draft's 70 package commands using two lanes, and 37.9 seconds for three native history checks separately. The base source had 64 package commands; the held draft added six, with none removed. The draft's complete 73-command CI inventory using three lanes passed in 91.2 seconds, including compilation; that presentation gate took 61.2 seconds. These are scoped development measurements, not acceptance of later source edits or a general host-performance guarantee. Final repair evidence records the exact checked inventory and source. The deadline bounds failure under load; it does not turn a stalled assertion into a pass. CI queueing and dependency installation are separate. No runtime service, machine resource allocation, storage policy or production pacing changes accompany check scheduling.
